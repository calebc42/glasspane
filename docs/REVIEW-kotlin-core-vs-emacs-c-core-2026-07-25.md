# REVIEW — Jetpacs Kotlin core vs the Emacs C core (2026-07-25)

**Question:** if Kotlin is to Jetpacs what C is to Emacs, what patterns, primitives, or implementations from the Emacs C core should the Kotlin core adopt?

**Scope guard applied throughout:** the Kotlin core interprets the EBP protocol and the Jetpacs DSL and renders it natively. It is NOT an Elisp interpreter and this is NOT a project to rebuild Emacs in Kotlin. Every recommendation went through a filter that rejected anything that (a) exists only because C lacks what Kotlin has, (b) Compose/coroutines already provide, (c) is wrong for the companion scale computed from SPEC 4.5 limits, or (d) misread either codebase.

**Method:** 10 companion-area x Emacs-C-subsystem pairings, each finding adversarially re-checked. Emacs read at the `emacs-30.1` tag; Kotlin claims probed against the pinned `org.json:json:20240303` jar and, where behavioral, measured. 30 recommendations survived, 2 rejected outright, plus 4 gaps from a completeness critic.

**Execution plan derived from this review:** `PLAN-emacs-informed-execution-2026-07-25.md` (start there; this doc is the detail).

**Adoption decisions from a 10-pairing review of `llm-poc-2/companion` (17.8k LOC) against `emacs-30.1`.**

Companion cites are absolute-path-relative to `/home/calebc42/pkb/projects/jetpacs/jetpacs/llm-poc-2/companion`.

## Part 1 — Live defects

These are bugs today. They are separable from Part 2 and should not wait on any architectural work, though three of them are dissolved for free by Tier-1 items.

### P1 — silent wrong data, or a user-visible break

**LD-1. A dialog `text_input` that submits via `dialog.submit` hangs the Emacs side forever.**
`/companion/wire/.../SpecValidator.kt:923-928` accepts `on_submit: {"builtin":"dialog.submit","capture_fields":[…]}` — correctly, because SPEC.md:1383-1385 explicitly blesses it ("except that `on_submit` inside a dialog MAY use the `dialog.submit` builtin"). The renderer's dialog rebinding, however, lives *only* in `Renderer.kt:525-548 onButton`, reached from five button-shaped call sites. `text_input`'s Done key goes straight to `ctx.action(onSubmit, v)` (`Renderer.kt:257`) → `CompanionEngine.dispatchAction` → `:255 if (descriptor.has("builtin")) return executeBuiltin(...)` → the `when` at `:208` has no `dialog.submit` arm and falls off the end, with a comment admitting it (`:237-239`, verified verbatim). The outstanding `dialog.show` request is never answered; Emacs waits until `rpc.cancel` or timeout. The blast radius is wider than `on_submit`: `on_tap` is not in the §14.3 injection table, so `{"t":"box","on_tap":{"builtin":"dialog.dismiss"}}` inside a dialog is fully conformant and equally dead (`LayoutNodes.kt:197`), as are `empty_state` (`ContentNodes.kt:319`) and `section_header` trailing (`LayoutNodes.kt:589-594`). *Fix: Tier-1 item 3 (override chain in `RenderCtx.action`), ~10 lines.*

**LD-2. The value on screen and the value sent to Emacs are different values.** *(converged: `redisplay-diff` and `buffer-local-variables` pairings, independently)*
`SurfaceStore.drafts` (`SurfaceStore.kt:40`) is authoritative for both `capture_fields` (`CompanionEngine.kt:277-278`) and §15.1 `input_state`. Every widget keeps a private Compose copy keyed only on `(surface, id)` — `Renderer.kt:236-238`, `InputNodes.kt:185, 205, 251-253, 363, 379` — both keys invariant across revisions, so the seeding lambda runs once and no later snapshot reseeds the field. Repro: Emacs pushes `text_input id="title"` rev 1; the user types "reject me"; Emacs rejects it and pushes rev 2 with `value:"Untitled"` and `reset_input_ids:["title"]`. `reconcileDrafts` (`SurfaceStore.kt:262-280`) erases the draft exactly as §13.6 MUSTs require, so `currentValue` now returns "Untitled" — but the field still reads "reject me", because `rememberSaveable` never re-ran. A button with `capture_fields:["title"]` then submits "Untitled" while the user is looking at "reject me"; the next keystroke publishes "reject mex" and the reset is silently undone. The mirror image fires on every process restart: drafts are durable, Compose state is not, so `input_state` reports a value that is nowhere on screen — defeating the point of persisting drafts. `grep reset_input_ids` returns zero hits in `app/`.

**LD-3. Dialog capture invents `""` for any field the user did not touch — the wrong JSON *type*, not just the wrong value.**
`DialogContext.fields` (`Renderer.kt:56-62`) is an overrides map created empty (`Renderer.kt:114`) and written only on user edit (`Renderer.kt:94`). Capture hardcodes the miss: `fields.put(fieldId, dialog.fields[fieldId] ?: "")` (`Renderer.kt:537`, verified verbatim; it is the sole dialog capture site). A dialog `checkbox` authored `checked: true` that the user never toggles ships the *string* `""` where SPEC.md:2315-2317 requires `fields` to "contain exactly the named current values keyed by node ID" — i.e. boolean `true`. The defaults already exist and are thrown away: `handleDialogShow` calls `SpecValidator.validateSurfaceSpec(...)` as a bare statement (`CompanionEngine.kt:1414-1421`) and discards the returned `statefuls` map. `DialogTest.kt:81-87` only covers the touched case.

**LD-4. Editor caret and selection go on the wire as UTF-16 code units, unordered.** *(converged: `text-storage-and-positions` and `markers-and-position-adjustment`)*
`Renderer.kt:363-364` (verified verbatim above) passes Compose's `value.selection.start/.end` — UTF-16 units, anchor/focus order — through two pure pass-throughs into `CompanionEngine.editorCommand:1185-1186`, which serializes them as `cursor`/`sel_start`/`sel_end` with no conversion, no clamp, no ordering check. Two independent MUST violations on one line: SPEC.md:2590 ("A Companion whose native editor uses UTF-16 code units … MUST convert before sending") and SPEC.md:2640 (`sel_start <= sel_end`). Repro: ten emoji, caret at end → reports `cursor: 20` against a 10-scalar document, so the allowlisted command runs at the wrong point or is rejected. Backward drag → `sel_start > sel_end`. Note the contrast one line away: the *text* path (`Renderer.kt:341` → `EditorSession.diff`) is scalar-correct, and the sibling caret path `setCaret` (`EditorSession.kt:72-85`) does validate ordering. `editorCommand` is the one wire path that bypasses `EditorSession` entirely.

**LD-5. The editor shadow has no owner, so §19.4's apply gate is not merely unchecked — it is uncheckable.**
`CompanionEngine.editorListener` (`:1106`) is declared and invoked (`:1229`, `:1248`) and **assigned nowhere outside `EditorTest.kt`** (grep confirmed above; `DeviceBridge.kt:254-314` subscribes eight listeners and not this one). Meanwhile `RenderEditor` owns its own `TextFieldValue` (`Renderer.kt:318-321`), keyed on `(surface, id)`. So after any inbound `edit.apply`, `s.shadow` moves and the on-screen text does not; the next keystroke diffs against a stale base and ships a splice that `splice()` accepts, because `splice()` validates only bounds and the length equation. §19.4's second gate — "the current editor text still equals its synchronized shadow" — cannot be evaluated while two objects own the text. Compounding it: `EditorSession.splice()` ends with three unconditional assignments (`EditorSession.kt:41-43`, verified verbatim) that *overwrite* rather than adjust the caret and destroy any selection — correct for a local keystroke (Emacs's `SET_PT`), wrong for an inbound apply (Emacs's `adjust_point`), and the same function serves both callers (`:1141`, `:1241`). And `handleEditApply` papers over it with `(params.opt("cursor") as? Number)?.toInt()?.let { s.setCaret(...) }` (`:1244-1247`): `cursor` is REQUIRED in §19.4's text-changing form but treated as optional, and `setCaret`'s `false` return is discarded, then `:1249` responds `{status:"applied"}` regardless.

**LD-6. Deferred editor opens are never pruned, leaking unreachable sessions and emitting `edit.open` for removed surfaces.**
`pendingEditors` (`CompanionEngine.kt:614`) is only ever added to (`:649`), cleared wholesale (`:149`, `:434`), and drained (`:433`) — grep confirmed, five sites, no pruning. Both removal paths (`closeEditor:1195`, `closeSurfaceEditors:658`) operate on `editors`, which a pending entry was never inserted into, so both are silent no-ops. `surface.update` and `surface.remove` are both legal in SYNCING (`MethodRegistry.kt:22-23`). Repro A: rev 1 puts editor `e` on document `d1`; rev 2 moves `e` to `d2`; on `session.ready` **both** are opened, `editors` holds `(d1,e)` and `(d2,e)`, but `surfaceEditors` names only `d2` — the `d1` session is unreachable by every close path, leaks for the connection's life, and is invisible to the `max_editor_sessions` count (`:583-590`, which sums `surfaceEditors`, not `editors.size`) while `handleEditApply` will still resolve and mutate it. Repro B: `surface.remove` during SYNCING, then `session.ready` sends `edit.open` for an editor on a surface that no longer exists.

**LD-7. Syntax highlighting silently stops at 20,000 characters.**
`highlightSpans(..., maxChars: Int = 20_000)` (`SyntaxHighlight.kt:116`, verified verbatim) and every tokenizer applies `val n = minOf(src.length, maxChars)` (`:176`, `:294`, `:355`). `highlightOrg`'s own 40,000 default is unreachable dead code because `:120` forwards the outer 20,000. All three call sites take the default (`Renderer.kt:247`, `Renderer.kt:329`, `ContentNodes.kt:146`). SPEC.md:238 floors `max_editor_bytes` at 65536, so on a 64 KiB file roughly two thirds of the document renders as plain unstyled text, permanently, with no signal — the exact "unfontified areas revealed by scrolling" failure `jit-lock` was written to prevent (`emacs-30.1:lisp/jit-lock.el:190-194`). Note what Emacs did *not* do: it capped the chunk, never the document. **Fix is one line** — raise or delete the parameter; keep the `runCatching` fallback at `:117`. Do **not** build the chunk cache (Part 4).

### P2 — conformance and cost

**LD-8. Lone surrogates are admitted, then silently rewritten to `?`.**
`handleEditApply` takes splice text with a bare cast (`CompanionEngine.kt:1235`) and `EditorSession.splice` concatenates it into `shadow`. `edit.resync` then puts `s.shadow` on the wire (`:1270` → `encodeFrame` at `:1676`); verified on the reference jar, `{"s":"A\ud800B"}` re-encodes to bytes `7b 22 73 22 3a 22 41 3f 42 22 7d` = `{"s":"A?B"}`. SPEC.md:122 is an explicit MUST ("an unpaired surrogate escape is invalid and MUST be rejected rather than preserved or replaced") and `grep -rn surrogate` over the whole companion returns zero hits. Scalar counts stay aligned (Java emits one `?` per surrogate char) and `edit.resync` does recover once the shadow is well-formed, so the failure is silent *content* divergence against a non-conformant or buggy peer, not the unrecoverable desync originally claimed. Fix it in the parser (Tier-1 item 1), not at the callsite, and add the conformance test.

**LD-9. The wire boundary accepts a superset of JSON and coerces types.**
`FrameCodec.parseBody:126-154` hands `JSONTokener.nextValue()` straight through plus two hand-rolled compensating full-text scans (`exceedsDepthLimit:162`, `hasDuplicateMembers:198`, both run on every good frame — a valid 4 MiB body is walked three times). Probed against the exact reference jar (`org.json:json:20240303`, `gradle/libs.versions.toml:7`): `{n:1}` OK, `{'n':'v'}` OK, `[1,2,]` OK, `+1`/`007`/`0x10` accepted, bare `NaN`/`Infinity` silently become the *strings* `"NaN"`/`"Infinity"`, out-of-range integers return `BigInteger`, and neither `JSONObject` nor `JSONArray` declares `equals`/`hashCode`. SPEC §4.1 forbids all of it. The codebase already documents this class of divergence in a comment at `FrameCodec.kt:142-146` (reference org.json throws on duplicate keys; Android's does not) — meaning the conformance suite certifies against a decoder whose value mapping differs from the device's.

**LD-10. Node attributes are never type-checked; accessors coerce.** *(converged: `value-model` and `dispatch-tables-and-vocabulary`)*
`grep '"enabled"\|"content_padding"' SpecValidator.kt` returns nothing, and the required-member loop (`SpecValidator.kt:403-406`) is presence-only. Probed live: `{"content_padding":"5"}` → `optDouble` returns 5.0 (`LayoutNodes.kt:248`); `{"enabled":0}` → `optBoolean("enabled", true)` returns the *default* `true`, so a disabled node renders enabled (`InputNodes.kt:184`); `{"password":"true"}` → `true`, inside the validator itself (`SpecValidator.kt:416`). SPEC §4.1: "A receiver MUST NOT coerce among strings, numbers, booleans, arrays, objects, and `null`." Sharper case from the repo's own audit: `{"t":"section_header","title":{"secret":"internal"}}` — `optString` coerces the object to its literal JSON text and renders it as a heading. Meanwhile `contract.json` carries 93 `field_types` rows and 19 `enums` rows that **no Kotlin reads** (`grep FIELD_TYPES|ENUMS|field_types` → nothing), while `SpecValidator.kt:32` and `:192` hand-duplicate two of those enums and the other 16 go unvalidated.

**LD-11. There is no image cache at all.**
`RenderImage` is `produceState<Bitmap?>(null, url) { ImageLoader.load(url, limits) }` (`ContentNodes.kt:71-73`) and that is the only decode entry point in the tree; `produceState` is `remember + LaunchedEffect`, so leaving composition discards the bitmap and cancels the load. `RenderLazyColumn` disposes off-screen items (`LayoutNodes.kt:243-256`), so scrolling a list of images past and back re-runs the full `loadHttps` path — fresh DNS, fresh TLS handshake, up to 8 MiB re-downloaded, full decode — behind a 15 s deadline showing the broken-image placeholder. Same on `view.switch`, on backgrounding, and after a relaunch of a durably-present surface (`SurfaceStore.kt:41-56` reloads specs; nothing reloads pixels), even though SPEC §17.2 names a cache as the §13.5 disconnected-presentation mechanism. Ten identical avatars are ten concurrent sockets.

**LD-12. Aggregate decoded-image memory is unbounded, and an OOM kills the process rather than degrading.**
`decodeGuarded` enforces `maxPixels` and `maxDecodedBytes` *per image* (`ImageLoader.kt:236-238`), and SPEC.md:258 confirms the reading ("apply per image"). Nothing bounds the sum: `SpecValidator` caps a snapshot at 10,000 nodes and applies no per-type limit to `image`, and a non-lazy `column` composes every child (`LayoutNodes.kt:143-159`). A conforming surface with ~8 maximal 4096×4096 images (note `4096*4096*4 == 67_108_864`, which is *not* `>` the limit, so each passes) asks for ~512 MiB of native bitmap plus 8 MiB in-flight buffers each, with unbounded coroutine parallelism. And `ImageLoader.load`'s guard is `catch (e: Exception)` (`:46`, verified) — `OutOfMemoryError` is an `Error`, so it escapes the loader, escapes the `produceState` coroutine, and takes the process. The guard stack's fail-closed-to-null discipline does not cover the one failure that matters.

**LD-13. The outstanding-request map is unbounded and is never failed on close — an explicit §22.3 MUST.**
`private val pending = HashMap<Int, (JSONObject?, JSONObject?) -> Unit>()` (`CompanionEngine.kt:182`), written at `:189` with no cap and no deadline, drained only on a matching response (`:168`). `close()` (`:121-151`) clears the queue in-flight marker, dialogs, pie menus, editors, `surfaceEditors`, `pendingEditors` and detaches from `firing` — and never touches `pending`, so §22.3's "Outstanding requests fail locally" is also unmet. §22.3 names "outstanding request count" as a MUST-bound resource. Against an Emacs that is alive at TCP level but wedged in Lisp, a `text_input` with `on_change` originates one entry per keystroke (`Renderer.kt:275`) — ~10/s, and the durable harm is not the memory (the engine is per-connection and dies with the socket) but that hundreds of user actions never conclude and the `onQueueProblem` toast that `:332-334`'s callback feeds never fires. The inbound side is fine: `DeviceBridge.kt:316-322` is a blocking 8 KiB read feeding `engine.feed` synchronously, so TCP window is the backpressure.

**LD-14. Cost defect, not a correctness defect: `persist()` writes and fsyncs all state on every keystroke.**
`SurfaceStore.putDraft` calls `persist()` unconditionally (`:255`), which rebuilds the entire state — every present surface's full `spec` plus every tombstone record (retained up to `max_surface_ids` = 4096, `:207`) plus every draft — and `FileSurfaceBacking.replace` serializes the blob, `out.fd.sync()`, renames, then `force()`s the directory: two fsyncs per typed character. `SurfaceStore.kt:64-67` documents this as deliberate §15.1 conservatism, so it is not a bug — it is O(all persisted state) plus two flash barriers for a kilobyte-scale write. It runs on `ebp-dispatch`, not the UI thread, so typing does not jank; the harms are flash write amplification at ~10 Hz and every subsequent action queued behind it. The dominant scaling term is tombstone accumulation, not surface size.

**LD-15. `max_editor_bytes` is neither advertised nor enforced.** *(converged: three pairings)*
`grep max_editor_bytes` over all Kotlin returns zero hits (confirmed above). It is REQUIRED in the welcome whenever `editor.sync` is granted (SPEC.md:238), and `editor.sync` is advertised (`DeviceBridge.kt:64`); the sibling `max_field_bytes` is already pinned at the 65536 floor (`:73`). SPEC.md:2779's `editor-too-large` refusal is unimplemented. Consequence: the effective editor ceiling today is `max_frame_bytes` = 4 MiB, which is what makes every editor performance number in this review look bad. **Declaring it at the floor is the single cheapest way to make three Tier-3 performance items permanently unnecessary.**

**LD-16. A trigger set is committed durably, then reported as a storage failure.**
`TriggerFiringService.replaceSet:137-143` commits and arms inside `synchronized(this) { store.replace(...).also { runtime.armBaselines(...) } }` and *then* calls `onTimeScheduleChanged?.invoke()` — wired to `TriggerAlarms.reschedule` (`CompanionStores.kt:120`), a loop over `AlarmManager.setExactAndAllowWhileIdle` (`TriggerAlarms.kt:32-40`). A throw from that platform loop is caught by `handleTriggersSet`'s `-32603 "Storage failed"` (`CompanionEngine.kt:1044-1050`) and `triggerListener` is skipped, so Emacs believes the prior set is still armed (SPEC.md:3043-3049: acceptance MUST atomically replace, rejection MUST leave the prior set unchanged) while the new one is live and baselined. The sibling `handleRemindersSet:901-906` gets this right — commit in the try, respond, *then* notify. Reachability is low (minSdk 34 + `USE_EXACT_ALARM` auto-granted rules out the SecurityException path; what remains is PendingIntent transaction limits), but the fix is hoisting one line.

**LD-17. Builtin context legality is not validated; per-target builtins are advertised and never read back.**
`surface_profiles.<target>.builtins` is emitted (`NodeSupport.kt:56-80`, shipped at `CompanionEngine.kt:1546`) and there is no `builtinsFromProfiles` to match `nodeTypesFromProfiles` (`ContextlessEvents.kt:14-17`); `SpecValidator.Ctx` has `advertisedTypes` with no builtin peer, and `validateAction`'s builtin branch checks only `ACTION_SCHEMA` membership (`:923-928`). SPEC.md:1361's "invalid context MUST reject the containing document" is therefore unimplemented — the companion accepts and silently no-ops. Note the calibration: *advertisement* is a sender duty (SPEC.md:1341-1342), so this never breaks a conformant Emacs; it is validator completeness plus the §14.2 context rules, which is why it is P2 and LD-1 is P1.

### P3 — hygiene

**LD-18.** `CompanionEngine.close()` (`:121-152`) is unprotected and calls host listeners at `:136`/`:142` *before* `firing.detach(this)` at `:151`, which removes the dead engine from a device-lifetime `AtomicReference` (`TriggerFiringService.kt:55-57`). `close()` is itself called bare inside `DeviceBridge.serve()`'s `finally` (`:326-332`), so a throw there also skips `clearLiveSession` and `socket.close()` — a leaked FD plus a dead engine parked globally. No listener `close()` currently invokes can throw (both are `MutableStateFlow` assignments), so this is a guard against the next listener, not a live crash. Two edits: `runCatching { engine.close(...) }` in the `finally`, and hoist `firing.detach` above the callouts.

**LD-19.** `IconMap.cache` is an unbounded `ConcurrentHashMap` keyed on a wire string (`IconMap.kt:17, 89-100`), and `icon.name` has no `"icon"` case in `validateNode` at all. The sharper half is length, not count: the `IDENTIFIER` regex (`SpecValidator.kt:21`) has no length bound, and `WireLimits.MAX_IDENTIFIER_OCTETS = 128` already exists (`FrameCodec.kt:22`) and is not applied — here, nor at `:245`, nor at `:259`. Add the `"icon"` case with both checks; the LRU is optional.

## Part 2 — Architectural recommendations, ranked by leverage per unit of work

### Tier 1 — do these three

**T1. Replace org.json at the frame boundary with a strict RFC8259 parser producing a sealed `EbpValue`.**
*Problem:* LD-9, LD-8, LD-10 — plus `FrameCodec.kt:137/:152` walking a 4 MiB body twice with hand-rolled scanners to patch a library whose policy is not EBP's policy.
*Emacs:* `etc/NEWS:34` — "Native JSON support is now always available; libjansson is no longer used." The replacement is `src/json.c`, 1,866 hand-written lines. Lone surrogates die at `json.c:1160-1181` (`json_signal_error (parser, Qjson_invalid_surrogate_error)`, with the comment "is the second half of the surrogate pair without the first half"). The entire number grammar is gated by one line at `json.c:1291` — `if (c < '0' || c > '9') json_signal_error (parser, Qjson_parse_error);` — which kills `+1`, `NaN`, `Infinity`, and `0x10` at the first character. Out-of-range is `Qjson_number_out_of_range` (`:1267`), not a silently widened representation.
*Why Emacs needed it:* Emacs ran the naive version — delegate the wire boundary to a general-purpose library and patch its behavior from outside — for three major releases (27–29) and abandoned it. The library's laxity, number mapping, duplicate-key and surrogate policy were not Emacs's policy, and none of them are correctable from the caller's side; you can only re-scan the text afterward, which is exactly what `FrameCodec` does twice. Writing the parser was the cheaper correct answer, and it let the parser produce the internal value type directly instead of translating a foreign one.
*Kotlin shape:* one file in `wire/`, 250–350 lines. `sealed interface EbpValue { EObj(Map<String,EbpValue>); EArr(List<EbpValue>); EStr; ENum; EInt; EBool; ENull }` plus `object EbpJson { fun parse(text: String): EbpValue }`. Enforce in-parse, one pass: duplicate member names (deletes `hasDuplicateMembers` and its scan), depth ≤ 64 by counter (deletes `exceedsDepthLimit` and its scan), unpaired `\uD800`–`\uDFFF` rejected, integers outside ±9007199254740991 rejected, no non-finite literals. `FrameDecoder.feed` changes element type to `EObj`. Budget ~+200 net lines after the ~80 deleted.
*Threshold:* none — this is conformance, and it is the substrate the next two items stand on.

**T2. One owner for the editor text, and positions that cannot be confused.** *(converges LD-4, LD-5, and the `text-storage` / `markers` pairings)*
*Problem:* the shadow lives in `EditorSession` and the text lives in a Compose `TextFieldValue`, with `editorListener` unsubscribed; and scalar and UTF-16 offsets are both bare `Int` so they meet on `Renderer.kt:363`.
*Emacs:* `src/buffer.h:988-995` states the discipline outright — "The `..._BOTH` functions take both a charpos and a bytepos, which must correspond to each other. The functions without `..._BOTH` take just a charpos, and compute the bytepos from it." — machine-checked at `src/insdel.c:93-95` (`eassert (charpos == BYTE_TO_CHAR (bytepos) && bytepos == CHAR_TO_BYTE (charpos));`), with conversion always a named call (`CHAR_TO_BYTE`/`BYTE_TO_CHAR`, `buffer.h:1057-1070`) and both members carried side by side in the struct (`buffer.h:234-237`). On ownership, `src/insdel.c:318-322` draws the line the companion's `splice()` erases: `adjust_point`'s comment, "This is used only when the value of point changes due to an insert or delete; it does not represent a conceptual change in point as a marker."
*Why Emacs needed it:* before Emacs 20, `charpos == bytepos` was simply true, and every site that conflated them was correct. When multibyte arrived, each of those sites became a silent wrong-position bug — the same failure shape as an off-by-one-per-emoji cursor. The answer was not a one-time audit; it was to make the duality unspellable by accident. Ownership is the same story from the other side: the set of position-holders is open-ended (point, mark, window start, process filter marks, overlay ends) and none of them are on the stack when a distant `insert` runs, so positions must live with the text.
*Kotlin shape, four parts:* (a) `@JvmInline value class ScalarPos(val v: Int)` / `Utf16Pos(val v: Int)` — both erase to `Int`, zero ART cost — pushed through `EditorSession` and every `CompanionEngine` editor signature, with exactly one named conversion pair on `EditorSession`, plus a `ScalarRange` whose factory applies min/max so SPEC.md:2640 holds by construction. Fix `Renderer.kt:363` by converting against the string the renderer holds. (b) Delete `EditorSession.kt:41-43`; `splice()` becomes text-in/text-out. `localEditorEdit` sets the caret at the call site (`SET_PT`); `handleEditApply` makes `cursor` required (`?: return respondError(-32602)`, matching the sibling at `:1223-1224`) and treats a false `setCaret` as `{status:"stale"}`. For the residual out-of-range/resync cases add one `adjustPositions(from, del, ins)` applying Emacs's three cases from `insdel.c:263-272` to the three existing `Int`s — **not** a `Marker` registry (Part 4). (c) Assign `editorListener` in `DeviceBridge.kt` alongside the other eight, expose the session (`CompanionEngine.editors` is private today, and `DeviceBridge.editorCommand` takes bare `Int`s — name that as part of the work), and render from it with an explicit `TextRange`, because `TextFieldValue(s.shadow)` resets the caret to 0. (d) Take Emacs's identity shortcut from `src/marker.c:179-183` — "If this buffer has as many characters as bytes, each character must be one byte… `if (best_above == best_above_byte) return charpos;`" — as three lines: cache `scalarLen`, and open `offset()` with `if (scalarLen == shadow.length) return scalarIndex`. That makes every conversion O(1) for every BMP-only document, CJK included.
*Threshold:* one remote edit and one concurrent local caret. This is a prerequisite, not an optimization.

**T3. One reconciliation point for input values, with a defaults layer extracted once.** *(converges LD-1, LD-2, LD-3 — three pairings)*
*Problem:* three symptoms of one missing structure: the wire draft store has no way to tell the screen it changed; the dialog store has the same shape with the defaults layer simply absent; and the dialog rebinding is open-coded at 5 of ~20 call sites.
*Emacs:* `Lisp_Buffer_Local_Value` (`src/lisp.h:3117-3159`) is a defaults-plus-overrides store with *one* storage location and a validity-stamped cache: `blv->where` records which buffer the loaded binding belongs to, and every read runs `swap_in_symval_forwarding` (`src/data.c:1546-1567`) which reloads on a stale stamp and falls through `local_var_alist` → `defcell` — `if (!(blv->found = !NILP (tem1))) tem1 = blv->defcell;`. The delete side is mandatory, not optional: `reset_buffer_local_variables` (`src/buffer.c:1165-1172`) — "Need not do anything if some other buffer's binding is now cached. `if (BASE_EQ (SYMBOL_BLV (XSYMBOL (sym))->where, buffer))` … Symbol is set up for this buffer's old local value: swap it out!" The display analogue is `make_current` (`src/dispnew.c:2771`): the accepted desired row *becomes* the current row in exactly one function — `assign_row (current_row, desired_row); current_row->enabled_p = true;` — and `dispnew.c:3776-3782` is a scar from letting a stale current row survive ("the third redisplay might be tempted to optimize redisplay based on lines displayed in the first redisplay"). The dispatch half is `Fkey_binding` (`src/keymap.c:1830`), which is nothing but `Flookup_key (Fcurrent_active_maps (Qt, position), key, accept_default)`, and `command_remapping` (`keymap.c:1243`), which resolves overrides *once* in the command loop (`keyboard.c:1496-1499`) rather than at each caller.
*Why Emacs needed it:* each is the same abandonment. Letting every reader keep its own copy of a buffer-local broke at `kill-all-local-variables`; letting each display component cache its own idea of the glass broke at three-redisplay staleness; letting each invocation site ask "am I in the special mode?" broke the moment two modes wanted to override one command or one call site was missed. LD-1 *is* that missed call site.
*Kotlin shape, three small pieces:* (a) `SurfaceStore` gains `private val epochs = HashMap<Pair<String,String>, Long>()` bumped whenever the displayed value was decided by a new snapshot rather than by the user — `reconcileDrafts` erasures (`:279`), `remove()` (`:217`), *and* update() when a node holds no draft but its authored value or value schema changed (that broader rule is what subsumes the ad-hoc `LaunchedEffect(optSig)` prune at `InputNodes.kt:256-262`, labeled "audit I7" — evidence the codebase is finding these one widget at a time). Widen `surfaceListener`/`onSurfaceChanged` (`DeviceBridge.kt:254-266`) to carry `values` and `epochs` on the dispatch thread, and add the epoch to the remember keys at the five input sites. Leave `Renderer.kt:318` (editor) off this helper — `SpecValidator.kt:564` keeps synchronized and `publish_state:false` editors out of `statefuls`, so it must keep seeding from the node and reseed on presentation identity (SPEC.md:1241-1244); T2 owns that path. Put `t` in the shared `"in:"` key while you are there. (b) `DialogContext` gains `defaults: Map<String, Any?>` from the `statefuls` map `handleDialogShow` already computes and discards, and one lookup: `fun current(id) = if (fields.containsKey(id)) fields[id] else defaults[id]`. `containsKey`, not `?:` — that is `blv->found`, so a deliberately-cleared field is not silently replaced. Promote `SurfaceStore.authoredValue` (`:316-324`) to shared so both stores use one implementation. (c) Move the dialog rebinding out of `onButton` into `RenderCtx.action` (`Renderer.kt:78-80`) as an ordered override chain — dialog map first — so the fifteen bypassing hooks become correct with no edit and `onButton` collapses. Do **not** extend the chain to `view.switch`/`trigger.fire` (Part 4).
*Threshold:* revision 2 of any surface, and the first dialog with an untouched captured field. Roughly 80–100 lines total across the three.

### Tier 2 — cheap and worth doing next

- **Bound `pending` and fail it on close** (LD-13). `max_outstanding` in the limits object, two watermarks with hysteresis — stop originating non-essential requests at half, take §22.3's `1401 overloaded` exit and `close()` at the cap. ## Part 3 — The deepest lesson

**Every P1 defect in this review is the same defect: two authorities for one fact, and no structure that makes one of them wrong.**

Look at the list. `org.json`'s value model versus SPEC §4.1's — LD-9, LD-10, LD-8. Compose's `TextFieldValue` versus `EditorSession.shadow` — LD-5. Compose `remember` versus `SurfaceStore.drafts` — LD-2. `DialogContext.fields` versus the authored defaults the engine computed and threw away — LD-3. A UTF-16 `Int` versus a scalar `Int` — LD-4. The advertised builtin profile versus three hand-written `when`s — LD-17, LD-1. `pendingEditors` versus `editors` — LD-6. `contract.json`'s `field_types` versus a per-node-type `when` — LD-10. In not one of these cases did anyone write the wrong logic. In every case someone wrote *correct* logic against a copy that a second, equally correct piece of logic had already moved on from.

The naive response is discipline: audit the call sites, add the missing subscription, remember the dialog check. The companion is already doing this, and you can see it in the code — `LaunchedEffect(optSig)` with the comment "audit I7" (`InputNodes.kt:258`), the `hasDuplicateMembers` scanner bolted onto a parser that will not enforce the rule, `NodeSupportPinTest`'s source scan, `VocabularyDriftTest`. These are all correct, all cheap, and all *per-instance*. They fix the case that was found. They do nothing about the case that was not.

Emacs's C core is organized around the opposite response, and it is worth stating precisely because it is easy to mistake for something else. It is **not** "have one global source of truth" — Emacs is full of caches and derived copies. It is: *every derived copy carries, in its own structure, the identity of what it was derived from, and the deriving code is the only code that can write it.* `blv->where` records which buffer the loaded binding came from, and every read checks it. `where_is_cache_keymaps` records which keymaps the reverse map was built over, `store_in_keymap` flushes it as its first statement, and `Fwhere_is_internal` re-validates on use. `img->timestamp` and `filter_image_spec` record what the decode was keyed on. `row->hash` records the row's content. `CHECK_STRING` at the DEFUN boundary versus `XSTRING`'s bare `eassert` inside records *where* the type was established, so "already validated" is a global, greppable property rather than a per-callsite habit. `make_current` records the moment a desired row becomes the current one, in exactly one function. And when Emacs cannot make the derived copy safe, it deletes the second authority outright: the text lives in one buffer, and everything that points into it — point, mark, markers, overlays — is registered with that buffer and adjusted by the one function that mutates it.

The consequence is structural rather than disciplinary. In Emacs you do not have to remember to invalidate the where-is cache when you define a key, because `define-key` cannot reach the binding except through `store_in_keymap`. In the companion you *do* have to remember to reseed the Compose field when a draft is erased, because nothing connects them — and LD-2 is what happens when someone doesn't.

So the architectural instruction this codebase should take is narrow and actionable: **when you find yourself with a second copy of a fact, do not add a synchronization step — add a stamp and a chokepoint.** A stamp is the epoch in T3, the `where` in `blv`, the seq already on §19.5 annotations (which the companion gets *right*, and which is why the marker machinery is unnecessary there). A chokepoint is `EbpJson.parse`, `RenderCtx.action`, `EditorSession.splice`, `SpecValidator`. The three Tier-1 items are each one stamp and one chokepoint, and between them they close eight of the nine P1/P2 defects that are not about images. That is not a coincidence; it is the lesson.

The corollary is a rule for reviewing new code here: *whenever a value is read in two places, ask which one the wire sees.* If the answer is "the other one," that is a defect, whether or not anyone has hit it yet.

## Part 4 — What we deliberately are NOT taking from Emacs

Each of these was proposed, investigated against both trees, and rejected for a stated reason. Re-proposing one requires refuting the reason.

**Data structures whose problem EBP designed away**

- **An interval tree for spans (`src/itree.c`).** `itree.c`'s two reasons to exist are the augmented LIMIT field for overlap queries and the OFFSET/otick lazy-shift machinery (`itree.c:99-128`). SPEC §19.5 states runs "MUST be sorted, MUST NOT overlap, and MUST fit the synchronized text" (SPEC.md:2792-2794), so a sorted `IntArray` plus binary search gives the same O(log n + k) with none of the code; and "MUST discard an annotation whose session or sequence does not match" means annotations never survive an edit, which deletes OFFSET's entire purpose. Emacs needs the tree because overlays are unbounded — its own comment cites "300KB and 30K overlays" as still a bottleneck (`marker.c:159-160`). The companion caps out around 10³–10⁴ spans, where a flat array shift is microseconds.
- **A gap buffer or a rope.** `StringBuilder` is the useful half and ships in the JDK. Measured: at the 65536 floor the current substring+concat rebuild is 0.017–0.071 ms, on a background thread.
- **A marker registry with `insertion_type`.** §19.4 makes `cursor` REQUIRED on every text-changing apply, so the caret's post-splice value is dictated by the peer, not derived by adjustment. A `class Marker(var pos, val insertAfter)` is ceremony around three `Int`s that the wire overwrites on the common path. Take the three-case adjustment arithmetic from `insdel.c:263-272` as a private function; leave the registry.
- **Marker adjustment for §19.5 annotation ranges or §19.3 completion positions.** These are seq-stamped and MUST be discarded on mismatch; the companion already does this correctly (`CompanionEngine.kt:1307`, `:1326`). Retrofitting adjustment here would be a spec violation, not an improvement.
- **A symbol interner / obarray for member names.** Emacs interns because symbols are compared in the evaluator's innermost loop *and* carry mutable per-name state (value cell, function cell, plist) that must be shared by identity. EBP member names carry no state, and the comparison targets are class-file string literals the JVM already interned. At the 10,000-node cap the whole key-comparison budget is sub-millisecond.

**Designs Emacs itself abandoned**

- **Preemptible rendering.** `redisplay-dont-pause` defaults to `true` (`dispnew.c:3252`, `:6912`) and the variable is obsolete (`etc/NEWS.24:24`). The DEFVAR comment says why: "Contrary to expectations, a value of \"false\" can be detrimental to responsiveness since aborting a redisplay throws away some of the work already performed. It's usually more efficient … to let the redisplay terminate, and just completely skip the next command's redisplay." The companion already has the replacement — `MutableStateFlow` (`MainActivity.kt:31`) conflates superseded snapshots by construction. Do not add a pending-input check, a cancellation token, a chunked composition pass, or a `withFrameNanos` yield loop.
- **`nimages > 40` eviction-delay shrink (`image.c:2371-2372`).** That population term is a proxy for memory pressure that Emacs's time-only eviction policy cannot measure. A byte budget measures it directly; adding the proxy on top is cargo-culting the workaround instead of the lesson.

**Things Kotlin, Compose, or the existing structure already provide**

- **A specpdl / unwind stack.** Traced every state machine named in the brief: the replay pump's flags are idempotent or released in `close()`; dialog and pie-menu teardown already consume the entry before running its effect (`CompanionEngine.kt:133-143`) — Emacs's `unbind_to` discipline, hand-written and correct; `SurfaceStore.update()` is validate-everything-then-mutate; and the two places needing compensating rollback already write `record_unwind_protect` longhand correctly (`DurableQueue.admit:139-155`, `TriggerFiringService.admit:169-181`). `unbind_to`'s pop-before-run property is what C needs because it has no lexical unwind scoping across frames; nested `try/finally` gives it for free.
- **`safe_funcall` around all host listeners.** `safe_funcall` is a redisplay-specific muzzle — its own comment says "This function started its life in 'xdisp.c' for use internally by the redisplay" — and Emacs lets `run-hooks` signal freely everywhere else. The companion's dispatch loop already fails closed (`CompanionEngine.kt:96-104`, "A dispatch failure must fail closed, never crash-loop the host"), all 18 callout sites are last-statement-in-handler, and the listeners are first-party app code, not user Lisp. Muting them trades a loud failure for a silently wrong UI.
- **A `Scoped<T>` primitive for per-surface theme or config.** §18.4 makes `theme.set` a single global replacement (`ThemeModel.kt:124-142`, one `CompositionLocalProvider`), and Compose's `CompositionLocal` already *is* default-plus-override-with-a-defined-lookup-order. There is nothing to model.
- **A realized-style cache keyed on (theme revision, role).** Emacs realizes faces because realization means *font selection* — matching a pattern against every font on the system (`xfaces.c:126-133, 163-178`), milliseconds of work. The companion's equivalent is `resolveColorIn` (`ColorModel.kt:43-84`), a `when` over ~24 interned strings, plus ~45 hex parses once at the root. It would buy nothing and add an invalidation bug surface. The one genuinely expensive realization, tokenization, is already memoized correctly (`ContentNodes.kt:144` keys on all three inputs; verified by disassembly that `SyntaxTransformation.filter` is already wrapped in a `remember` inside `CoreTextField`).
- **A refcount on cache entries.** Emacs needs `img->refcount` and `SET_FRAME_GARBAGED` after `uncache_image` (Bug#6426) because `free_image` actually releases the pixmap while glyph matrices hold the id — a dangling-reference problem C has and Kotlin does not. An on-screen `Image(bitmap = …)` holds a strong reference; evicting the map entry cannot pull it out from under a draw. (Do keep honest *accounting* for an evicted-but-still-composed bitmap.)
- **Compose's own diffing, recomposition, and structural equality.** The companion's problem is not that Compose's diffing is inadequate — it is that passing `JSONObject` parameters switches it off. Fix the inputs, do not build a differ.

**Things that would be net-negative here**

- **Cooperative quit (`maybe_quit`) or a work budget inside `SpecValidator.walkNode`.** `FrameCodec.exceedsDepthLimit` already implements the primitive that matters — a constant-stack pre-parse depth scan bounding recursion to 64 frames — and the body is capped at 4 MiB with the node walk capped at 10,000. Worst case is a linear pass over already-materialized JSON, dominated by the org.json parse that preceded it, on the socket reader thread which does nothing else and never touches the UI thread. `ensureActive()`/`yield()` would be pure ceremony.
- **A `while-no-input`-shaped abandon of a superseded `surface.update`.** Every `surface.update` owes a response; revisions from Emacs are monotonic so stale updates only appear on replay; and skipping validation on the stale path would change which of 1201-vs-stale wins for an invalid stale request — a conformance risk for a few milliseconds.
- **Generating the renderer's `when` from `contract.json`.** `contract.json` cannot know which of the 39 types *this build* implements or which Composable to call — that is exactly what positive-knowledge profiles express. `NodeSupportPinTest`'s source scan fails on set inequality, loudly. This is already correct.
- **Unifying builtin dispatch into one table with `run` lambdas.** The three `when`s are a module boundary, not duplication: `wire/` is Android-free by construction, so `clipboard.copy`/`share.send`/`companion.settings.open` need a `Context` (hence `hostBuiltinListener` as a per-engine `var`), and `dialog.submit`/`dialog.dismiss` can have no wire-side body at all because they read `DialogContext.fields`, a Compose `SnapshotStateMap`. Collapsing them means either dragging Android into `wire/` or a process-global mutable dispatch table. Take the *validation* half only. Likewise, do not extend T3's override chain to `view.switch`/`trigger.fire`: those must run on `ebp-dispatch` under the engine's `@Synchronized` to preserve §14.6 state-before-action ordering.
- **Wiring `gen-vocabulary.py` as a `compileKotlin` dependency, on the `store_in_keymap` analogy.** `where_is_cache` needs writer-side invalidation because it is a *runtime* cache with no checker. The companion's derived copy has a checker that runs on every build and in CI. This would trade a working deterministic check for a `python3` dependency in every build environment and IDE sync. Fix the drift test's under-scope instead.

## Part 5 — Build order

If the team does three things, do them in this order.

**1. Declare and enforce `max_editor_bytes` at the 65536 floor, and delete the 20,000-char highlight cap.** (LD-15, LD-7.) Two small edits in `DeviceBridge.kt:80`, `CompanionEngine.localEditorEdit`/`handleEditApply`, and `SyntaxHighlight.kt:116`. This goes first because it is the cheapest thing on the list *and because it decides the shape of everything after it*: with the ceiling at the floor, six Tier-3 performance items become permanently unnecessary and stay off the backlog, and the one user-visible rendering bug in the editor disappears. Leaving the ceiling implicitly at `max_frame_bytes` = 4 MiB is what makes the editor look like it needs a rope.

**2. The strict wire parser and `EbpValue` (T1).** Second because it is a leaf change with no dependents — one new file plus one changed element type — and because it is the substrate the type discipline in T3's validator work stands on. It closes LD-9 and LD-8 outright, deletes two full-body scans, and it is the only item here that converts an entire *class* of future bug into a parse error. Do it before the attribute-type work in Tier 2, so that work has a typed value to check against rather than a coercing accessor to work around.

**3. Editor ownership and typed positions (T2), then the reconciliation epoch and defaults layer (T3).** These are third and fourth because they are the largest, and because both are cleaner once T1 exists. Within them: T2 before T3, because the editor is the module that is currently *non-functional* for inbound edits — LD-5 means every `edit.apply` silently desynchronizes the display — whereas T3's failures, while worse in consequence (wrong data on the wire), require a specific push sequence to trigger. Inside T2, wire `editorListener` first: it is the change that makes §19.4's shadow-equality gate expressible at all, and everything else in that item is arithmetic.

Everything in Tier 2 is independently landable at any point; three items there are ~20-line crash- or hang-closers (`Semaphore` + `catch (Throwable)`, the `pending` drain in `close()`, the `RenderCtx.action` override chain) and are worth slipping in ahead of anything above if the calendar allows.

## Part 6 — Dropped, and why

Stated explicitly so they are not rediscovered:

- **Member-name interning** (R4) — never pays; see Part 4.
- **Delta-maintained `Z`/`Z_BYTE` counters** (R6) — superseded by declaring `max_editor_bytes` at the floor; the identity shortcut survives inside T2.
- **`TextFieldState`/`ChangeList` migration** (R7) — real API, real primitive, wrong price: multi-hundred lines through the most spec-load-bearing renderer path to save ~1 ms at a document size the Companion itself chooses. The 15-line allocation fix in `diff` gets the same win.
- **`StringBuilder` shadow as its own change** (R8) — do it as a byproduct of T2 or not at all.
- **jit-lock chunk cache** (R11 perf half) — Compose's `MultiParagraph` relayout dominates by an order of magnitude, and the cache would forfeit cross-chunk syntactic correctness that the current pass has for free.
- **Landmark/anchor conversion cache** (R10/R13 tier 2) — threshold is ~256 KiB or hundreds of §19.5 endpoints per push; neither is reachable.
- **`UiNode` IR as a near-term item** (R14) and **cached-hash + reuse pass** (R16) — deferred to Tier 3; the cheap scope split captures the realistic win.
- **Interruptible rendering** (R17) — Emacs deleted it and documented why.
- **Blanket `safeCallout` wrapper** (R21 second half, R22 part b) — would convert a loud fail-closed into a silently wrong UI.
- **Draining `pending` with synthetic errors as a *correctness* argument** (R22 part c) — both consumers are fire-and-forget; the drain is still worth doing for §22.3 conformance (Tier 2), not because a caller blocks on it.
- **`IconMap` LRU** (R30) — the length cap is the actionable half; the eviction is optional hygiene.

## 1. `src/fns.c` was never opened, and `JsonEquality.kt` got zero coverage — the review's own Part-3 thesis has a second instance it missed

**What to check:** `/home/calebc42/pkb/projects/jetpacs/jetpacs/llm-poc-2/companion/wire/src/main/kotlin/com/calebc42/ebp/wire/JsonEquality.kt` (all 18 lines) against `emacs-30.1:src/fns.c:2826-2872` (`internal_equal`) and `:1878-1889` (`same_float`).

The review has a **value-model** pairing and never opened the file that *is* SPEC §4.3 structural equality. It is called at 12 non-test sites, three of which are validator MUST-reject decisions (`SpecValidator.kt:471` duplicate option values, `:480` allow_add membership, `:489`) and three of which decide whether a user's draft is silently erased (`SurfaceStore.kt:276`, `:292`, `:303`).

Its last clause is `else -> a == b` — it delegates the terminal case to org.json's `equals`. **Probed on the pinned jar** (`org.json:json:20240303`):

```
NULL.equals(null) = true
```

So `jsonValueEquals(JSONObject.NULL, null)` is `true` while `jsonValueEquals(null, JSONObject.NULL)` is `false` (Kotlin's `==` dispatches on the left operand). The predicate is **asymmetric**, and in one direction it conflates JSON `null` with an absent member — against SPEC.md:131, verbatim: *"An absent member and a member whose value is `null` are distinct."* Kotlin `null` is exactly what `authoredValue` returns for an absent member (`SurfaceStore.kt:316-324`, e.g. `"enum_list" -> node.opt("value") ?: … null`).

Emacs's decisive line is the one `JsonEquality` lacks — a type-tag gate *before* any comparison, so no cross-type equality is reachable at all:

```c
  if (BASE_EQ (o1, o2)) return true;
  if (XTYPE (o1) != XTYPE (o2)) return false;
  switch (XTYPE (o1)) { case Lisp_Float: return same_float (o1, o2); …
```
`fns.c:2864-2872`. And `same_float` (`:1880-1889`) refuses C's `==` outright, comparing the bit words — because IEEE `==` is the wrong policy for an equality predicate. That is the same lesson as T1: **when the language's default equality isn't your spec's equality, you do not layer a `when` on top of it; you make the borrowed one unreachable.** The review diagnosed this at the parser and never traced it to the equality predicate the parser feeds.

Why it matters more than its size: `internal_equal` is the fix that costs ~6 lines (an explicit total `when` over the seven EBP types with no `else` fallthrough), it drops out of T1's `EbpValue` almost for free (a sealed hierarchy makes the missing-arm case a compile error), and the review's own build order puts T1 first without noticing that it dissolves this too. Two related notes: the number clause (`a.toDouble() == b.toDouble()`) is **conformant** per SPEC.md:160 ("`1`, `1.0` … equal by binary64 value") *provided* T1 lands its ">2^53 integers rejected" rule — worth stating as a dependency, because today org.json returns `Long` for `9007199254740993` and `9007199254740992` and they compare equal. And recursion is safe: depth is pre-bounded at 64.

## 2. `src/process.c` was never opened, and `FrameDecoder.feed` is O(n²) — measured, not speculated

**What to check:** `FrameCodec.kt:57-73` against `emacs-30.1:src/process.c:6162-6264` (`read_process_output`) and `emacs-30.1:lisp/jsonrpc.el:730-792` (the same protocol's Emacs-side decoder).

The review opened `FrameCodec.kt` twice (LD-9's double-scan, T1's rewrite of `parseBody`) and **never looked at `feed`**, which is the function above `parseBody`. Three separate full-buffer passes run on *every* transport read:

```kotlin
buffer += bytes                                   // :59  reallocate + copy all pending
val term = indexOfTerminator(buffer)              // :61  scan from index 0, every time
…
if (buffer.size < bodyEnd) return // retain partial data   // :69  returns WITHOUT consuming the header
```

Because `:69` returns without consuming, the next read re-scans the whole accumulated buffer for `CRLFCRLF` *and* re-runs `parseHeader` — on top of the realloc-concat. `DeviceBridge.kt:317` reads `ByteArray(8192)`, so a max-size frame is 513 iterations. I simulated the exact loop on this machine:

```
body=262,144    reads=33   wallclock=1 ms    memcpy=4,587,546 B      scanned=4,587,546 B
body=1,048,576  reads=129  wallclock=21 ms   memcpy=68,681,755 B     scanned=68,681,755 B
body=4,194,304  reads=513  wallclock=229 ms  memcpy=1,080,033,307 B  scanned=1,080,033,307 B
```

229 ms and 1.08 GB of memory traffic on a desktop, for one spec-legal frame, before a single byte is parsed. On a phone that is seconds. This is directly load-bearing on the review's own reasoning: LD-15 says the effective editor ceiling is `max_frame_bytes` = 4 MiB, and Tier 3 spends six rows arguing about editor performance at that size — while the frame that carries it costs a gigabyte of memcpy to receive.

Emacs's answer is exact and two-part. In C, `read_process_output` reads into a **fixed** buffer sized once per read — `chars = SAFE_ALLOCA (sizeof coding->carryover + readmax);` (`process.c:6183`), `readmax` from `read-process-output-max`, default 65536 (`:8911`) — and carries over only the *decoder's* partial-multibyte remainder (`:6176`, `:6382-6388`), never the accumulated message. In Lisp, `jsonrpc--process-filter` — Emacs's decoder for this identical framing — stores `expected-bytes` **on the connection** so the header regexp runs once and is bounded to `(+ (point) 100)` (`jsonrpc.el:739-745`), consumes with `(delete-region (point-min) (point))` (`:782`), and accumulates by `insert` into a gap buffer, which is amortized O(1) at `Z`. The naive version is exactly the companion's: re-derive parse state from the whole buffer on every chunk.

**Kotlin shape** (~30 lines, no new types): give `FrameDecoder` a `bodyStart`/`expected: Int?` pair and a `scanned: Int` watermark; accumulate into a `java.io.ByteArrayOutputStream` or a manually-grown `ByteArray` with a read offset instead of `buffer += bytes`; resume `indexOfTerminator` at `scanned - 3`; parse the header once. Threshold: it is already crossed — the review's own `max_editor_bytes` recommendation (Part 5 step 1) caps *editors* at 64 KiB but does nothing about `surface.update` snapshots, which are capped only by the 10,000-node / 4 MiB body limits. This belongs next to T1 in build order, not in Tier 3.
