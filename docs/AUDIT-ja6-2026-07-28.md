## The thesis

**The recurring thesis recurred, and it recurred in code written during this
same session.** Prior audits (JA-1/JA-2, JA-3, JA-4) all concluded: *the
invariant was written down, pinned with a test at ONE call site, and not applied
at the others.* JA-6 reproduces it three separate times:

1. `confirm` — the Companion fix written TODAY gates `confirm` in
   `DeviceBridge.dispatch` only. `CompanionEngine.dispatchDescriptorContextless`
   (pie menus, reminder taps) emits `event.action` on a wholly separate path and
   consults no confirmation. A destructive descriptor delivered that way fires
   unconfirmed — the exact defect the device gate had just caught, reintroduced
   one layer down. Hand-verified: `dispatchAction` has exactly one production
   caller; `sendRequest("event.action", …)` has five.
2. The wire-safe gate — applied at 6 of 8 `:args` path sites. `--up-row` and the
   editor descriptor skip it, and the module's own Commentary documents the rule
   they break.
3. `jetpacs-scalar-text` — every op notification sanitizes except `"Moved to %s"`.

**The second thesis also recurred**: *the module documents invariants it does not
enforce.* The `claims` lens found 8 statements in docstrings, commentary, commit
messages and the plan that the code does not deliver — including one in this
rung's closing evidence (below).

**New for this rung: the guard returns a value that is safe to CHECK and unsafe
to USE.** `jetpacs-check-path` resolves symlinks so containment cannot be
straddled — correct, and its docstring says exactly that. But every caller then
*operates on the resolved truename*, which silently substitutes the link's target
for the thing the user named. That is P1-1, and it is a design-level mistake in
the floor guard's contract, not a slip at one call site.

## P1 — fix before this rung is called done

### P1-1 · Destructive ops act on the resolved truename — an op on a symlink hits its TARGET

**Every file op acts on the RESOLVED truename, so deleting a symlink recursively destroys its target tree**  
`emacs/jetpacs-files.el:1097` · lens `sandbox` · 3/3 confirmed

*Claim.* `jetpacs-check-path` returns a truename, and `jetpacs.files.delete` (plus
rename/move/duplicate) act on that truename, so an op invoked on a symlink row
is silently applied to the link's TARGET instead of the link — for a link to a
directory this means `delete-directory TRUE t`, a recursive wipe of the target
tree, while the link itself survives.

*Reproduction.* Verified by running the handler body under emacs -Q. Fixture: root=/tmp/sbx…/,
root/target/ containing root/target/keep, and root/link -> root/target (both
inside the sandbox). `(jetpacs-files--check "…/link" nil)` returns "…/target";
`file-directory-p` is t; the handler then runs `(delete-directory "…/target"
t)`. Observed after: `(file-symlink-p "…/link")` => "…/target" (link still
present, now dangling), `(file-exists-p "…/target")` => nil, `(file-exists-p
"…/target/keep")` => nil. The user tapped the trash on a row labelled "link"
and confirmed "Delete link and everything in it?"; what was destroyed is
`target`, and after the deferred re-push the row named `link` is STILL in the
listing (dangling link, now rendered as a 0-byte file row), so the operation
looks like it failed while it actually ate a different directory. The same
substitution makes rename/move (jetpacs-files.el:873, 900) relocate the target
and leave a dangling link, and duplicate (jetpacs-files.el:915-917) copy the
target's contents. No test covers a symlink under any of the five ops
(test/jetpacs-files-test.el:926 exercises delete on a plain file and a plain
directory only).

*Fix.* Separate "path used for containment" from "path acted on". Have the ops act on
the LITERAL validated argument, not the returned truename: for delete, `(if
(file-symlink-p literal) (delete-file literal) …)` so a link is unlinked
rather than followed; for rename/move/duplicate pass the literal source to
`rename-file`/`copy-file` (both handle links natively) after confirming that
BOTH the literal path and its truename are contained. If following links is
genuinely wanted, the `:confirm` string must name the resolved target, not the
row label.

### P1-2 · The save path silently re-encodes the file (CRLF→LF, non-UTF-8→UTF-8)

**jetpacs.files.save silently re-encodes the file: CRLF becomes LF and non-UTF-8 becomes UTF-8, even on a no-op round trip**  
`emacs/jetpacs-files.el:1190` · lens `onecallsite` · UNVERIFIED (verifiers died on the session limit)

*Claim.* The no-visiting-buffer save branch calls `(write-region value nil true nil
'silent)` with no `coding-system-for-write`, so the decoded seed is re-encoded
with the ambient coding system instead of the file's own — silently rewriting
the whole file's bytes; the sibling `save-buffer` branch preserves `buffer-
file-coding-system` and does not.

*Reproduction.* Verified by execution against the real `jetpacs--dispatch`. (a) Write
`R/crlf.txt` with `coding-system-for-write` = `utf-8-dos` ("line one\r\nline
two\r\n"). Open it in the device editor (seed = `insert-file-contents` output,
LF only) and dispatch `jetpacs.files.save` with `:value` = that unmodified
seed. Status = `accepted`; the file on disk is now LF-only — every CRLF in the
file is gone. (b) Write `R/l1.txt` with `coding-system-for-write` = `iso-
latin-1` ("café\n" => bytes `caf\351\n`). Same unmodified round trip: status =
`accepted`, disk is now `caf\303\251\n` (UTF-8). Nothing on the device or in
the notification says the file changed; simply opening a file and tapping save
mutates it.

*Fix.* Capture the coding system at open time — bind it from `last-coding-system-
used` after the `insert-file-contents` in `jetpacs-files--edit-open` and store
it in `jetpacs-files--edit` alongside `:seed`/`:mtime` — then bind `coding-
system-for-write` to it around the `write-region` (and validate the stored
value is still current at save). Pin it with a test that round-trips a
`utf-8-dos` fixture and compares raw bytes, not `buffer-string`.

### P1-3 · The buffer save route is non-atomic: the buffer is destroyed before the write can fail

**Save through a visiting buffer clobbers the buffer before `save-buffer' can fail, with no unwind**  
`emacs/jetpacs-files.el:1184` · lens `actions14` · UNVERIFIED (verifiers died on the session limit)

*Claim.* The buffer route does `erase-buffer' + `insert value' BEFORE calling `save-
buffer', and `basic-save-buffer'/`basic-save-buffer-2' reach interactive-
recovery prompts (write-protected, require-final-newline) that signal
`inhibited-interaction' under the dispatch's no-prompts regime — so on failure
the handler answers `rejected' while the desktop buffer is left holding the
device's text as unsaved modifications that never reached disk.

*Reproduction.* Verified by running the real dispatch (emacs -Q --batch). Root contains
`init.el' ("(setq a 1)"), visited by `find-file-noselect', unmodified. `chmod
444 init.el' (a write-protected file — read-only checkouts, root-owned config,
a Syncthing-managed tree). Device sends `jetpacs.files.save' with a matching
`:mtime' and `:value' "(setq a 2) ;; DEVICE". Observed: status=`rejected',
note "Save failed: inhibited-interaction", DISK still "(setq a 1)", and the
visiting BUFFER now contains "(setq a 2) ;; DEVICE" with `buffer-modified-p' =
t. Emacs 30.1 files.el:6091 (`basic-save-buffer-2') is the `yes-or-no-p "File
%s is write-protected; try to save anyway?"' that fires after the mutation.
Downstream: the file is now permanently unsavable from the device — every
later save hits the `(and buf (buffer-modified-p buf))' guard at line 1170 and
answers `rejected' "Unsaved desktop edits" — and nothing tells the user their
desktop buffer diverged from disk.

*Fix.* Do not route the write through `save-buffer'. Write with `write-region' (the
branch at line 1190 that is already correct), then bring the buffer into line
with `revert-buffer'/`insert-file-contents' + `set-visited-file-modtime' only
after the write succeeded. If `save-buffer' must stay, snapshot the buffer
text and modified flag and restore both in the error path before answering
`rejected', and pre-check `file-writable-p' so the refusal happens before any
mutation.

### P1-4 · A FIFO or other non-regular file under a root hangs Emacs forever mid-scan

**A FIFO or other non-regular file under a root hangs the whole Emacs process forever mid-scan**  
`emacs/jetpacs-files.el:562` · lens `async` · 3/3 confirmed

*Claim.* The scan classifies every queue item as symlink / directory / "file" and never
checks file-regular-p, so a FIFO passes the symlink, directory, size (0 bytes)
and file-readable-p guards and reaches insert-file-contents at jetpacs-
files.el:484, which blocks in open(2) until a writer appears — freezing the
timer loop, the jsonrpc filter and the dispatch pump indefinitely.

*Reproduction.* Verified by execution:

  mkfifo /tmp/fifotree/pipe; echo needle > /tmp/fifotree/a.txt
  timeout 15 emacs -Q --batch -L emacs --eval '(progn (require (quote jetpacs-
files))
    (let (result) (jetpacs-files--grep-start "/tmp/fifotree" "needle" (lambda
(r) (setq result r)))
      (cl-loop repeat 500 until result do (accept-process-output nil 0.02))
      (message "result=%S" (and result t))))'
  -> Terminated, EXIT=143. No message ever printed.

Attribute check on the FIFO: file-readable-p=t, file-regular-p=nil, size=0 —
every one of the scan's four documented bounds passes it through. C-g does not
recover (Emacs retries the blocking open on EINTR), so the session needs kill
-9; the EBP connection dies with it and any unsaved desktop buffers go with
the process.

The module documents the opposite property in two places it does not enforce:
jetpacs-files.el:437-439 ("bounded four ways ... a C-level regexp match never
yields to timers" — the reason the query is kept a literal) and jetpacs-
files.el:506-509 ("each tick processes N items and re-arms a short timer, so a
large tree never wedges the event loop"). Default jetpacs-files-roots
(jetpacs-files.el:64-67) includes "~/", so any FIFO anywhere under $HOME
(mpd's fifo output, an mkfifo scratch, a tool's IPC pipe) is in scope, and the
user never selects it — the walk finds it on its own.

Same hazard on a user tap: jetpacs-files--edit-open (jetpacs-files.el:749-751)
reads with insert-file-contents after only a size check, and a FI

*Fix.* Add `((not (file-regular-p path)) nil)` to the cond at jetpacs-
files.el:546-570, ahead of the size check (file-regular-p follows links, but
symlinks are already dropped at :535). Apply the same guard in jetpacs-files--
edit-open before the read at :749 — that is the other call site of the same
missing invariant.

### P1-5 · The wire-safe gate is applied at 6 of 8 `:args` sites — one directory bricks the surface

*Claim.* `jetpacs-files--up-row` (line 295) and `jetpacs-files--edit-screen` (line 784)

module already checks the CONTENT for wire-safety but never the PATH, and
`jetpacs-files--check` returns a truename whose bytes come from the
filesystem, not from the wire. Same check is owed to `jetpacs-files--shared-

## P2 — conformance and robustness

**grep's per-file size cap is an on-disk cap, but insert-file-contents dispatches through file-name-handler-alist (gz bomb, gpg prompt)**  
`emacs/jetpacs-files.el:484` · lens `sandbox` · 3/3 confirmed

*Claim.* `jetpacs-files--grep-file` bounds the file by `file-attribute-size` (jetpacs-
files.el:557-561) and then reads it with `insert-file-contents`, which runs
`file-name-handler-alist`; jka-compr and epa-file therefore let a file that
PASSES the 1 MiB cap expand to arbitrary size (or block on a passphrase)
inside a single non-yielding scan tick, defeating the "bounded four ways" and
"chunked so a large tree never wedges the event loop" claims in the section
commentary (jetpacs-files.el:427-439).

*Reproduction.* Verified under emacs -Q (auto-compression-mode is t and epa-file-handler is in
file-name-handler-alist in a bare -Q session, both confirmed). Put a
203865-byte /tmp/big.gz (gzip of 200 MiB of 'A') anywhere under the search
root — it is 199 KiB on disk, well under `jetpacs-files-grep-max-file-bytes`
(1 MiB), is not a backup, is readable, and is not a symlink, so it reaches
`jetpacs-files--grep-file`. `(with-temp-buffer (insert-file-contents
"/tmp/big.gz") (buffer-size))` => 209715200. That 200 MB allocation + `search-
forward` scan happens synchronously inside one `step` tick between two `run-
at-time 0.01` re-arms, so the jsonrpc socket filter and the dispatch pump
stall for the whole read; gzip ratios of 1000:1 make a 1 MiB member ~1 GiB,
i.e. OOM territory. Second consequence, same line: a `~/.authinfo.gpg` or any
`*.gpg` under the root routes through epa-file, which will run a pinentry /
`read-passwd` from the timer (blocking Emacs on a desktop prompt nobody is
watching), and on success puts DECRYPTED secret lines into hit cards pushed to
the device. The `ignore-errors` at line 484 hides the failure mode but does
not stop the read.

*Fix.* Bind `(let ((file-name-handler-alist nil) (inhibit-file-name-handlers …)) …)`
around the `insert-file-contents` in `jetpacs-files--grep-file`, or read a
bounded prefix with `(insert-file-contents file nil 0 jetpacs-files-grep-max-
file-bytes)` so the cap bounds the READ rather than the stat. Additionally
skip names matching `jka-compr-load-suffixes`/`.gpg` outright — a content
search of an encrypted or compressed blob is not something the scan can do
honestly.

`emacs/jetpacs-files.el:1175` · lens `actions14` · UNVERIFIED (verifiers died on the session limit)

*Claim.* The handler's only buffer gate is `(and buf (buffer-modified-p buf))'; an
UNMODIFIED buffer whose file changed on disk since Emacs visited it still
routes through `save-buffer', which hits `basic-save-buffer''s
supersession/`Save anyway?' path and signals — so the save is answered
`rejected' (permanent) even though the handler's own mtime stamp gate passed

*Reproduction.* Verified by running the real dispatch (emacs -Q --batch). `find-file-noselect'

content-unchanged', which is why the existing test at test/jetpacs-files-
