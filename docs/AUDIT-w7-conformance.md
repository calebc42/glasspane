# Jetpacs W7 Conformance Audit (SPEC 17.6–21)

_Adversarial multi-agent audit, 2026-07-23. 16 module/cross-cut auditors → 126 raw findings → 77 survived adversarial refutation (47 refuted). Severity: 16 P1 · 33 P2 · 28 P3._

## Executive summary

The W7 reference implementation has a strong, well-tested wire/protocol core across every module — validation taxonomy ordering, capability gating, state-machine welcome/handshake, surface/dialog/pie/toast/theme lifecycles, editor scalar-position math, and the trigger replace-set/predicate/substitution logic are all substantially conformant and covered by unit tests. Conformance breaks down along two seams. First and dominant: durability and offline behavior for reminders (SPEC 18.6) and device triggers (SPEC 21.1/21.2/21.5) is essentially unimplemented. ReminderStore and TriggerStore are plain in-memory maps held as per-connection engine fields, while the engine itself is re-created on every socket in DeviceBridge.serve(), so accepted sets, fired receipts, throttle floors, one-shot/boot markers, and schedule anchors survive neither a process/device restart nor even a routine SPEC 5.2 reconnect — in direct contrast to the file-backed DurableQueue/SurfaceStore that are correctly hoisted to DeviceBridge and injected. This single architectural gap plus its Android-presentation consequences (no boot re-arm, no tap routing, no cancel-on-remove, no fired-receipt consultation, firing gated on a live session) accounts for the large majority of the P1 findings. Second: the Android platform-presentation layer is a stub relative to the wire layer — it drops theme colors/syntax, notification meta.actions, and editor read_only/inbound-edit rendering that the wire engine faithfully parses. Two isolated P1s round out the list: the renderer lets a read-only synchronized editor mutate the authoritative Emacs document (SPEC 17.4), and dialog.submit omits the mandatory pre-commit max_frame_bytes serialization check, wedging the modal and skipping §14.6 password erasure on overflow. The remaining P2/P3 findings cluster into validator-completeness gaps (several on_tap/action paths hand-roll a subset of validateAction) and latent security items that are dormant only because the reference config advertises just battery.level.

## Overall posture

NON-CONFORMANT as a reference implementation, but structurally close. The protocol/wire core is production-grade; the failures are concentrated and largely share root causes. The blocking work is (1) hoisting ReminderStore/TriggerStore into DeviceBridge with durable, keystore-capable file backing shared across connections (mirroring DurableQueue/SurfaceStore), (2) wiring the Android presentation layer (boot receiver, tap→§14 routing, cancel-on-remove, fired-receipt gating, theme colors/syntax, notification actions, editor read_only/inbound repaint), and (3) two localized fixes (editor read_only enforcement; dialog.submit prospective size check). Until the durable-store hoist and the trigger firing-order/offline-service rework land, reminders and triggers cannot claim conformance. Validator completeness and identifier-length bounds are non-blocking (P2/P3) but numerous and should be closed by routing every on_tap through the canonical validateAction and applying the shared 128-octet identifier cap uniformly.

## P1 findings (16)

### [SPEC 17.4] Renderer ignores editor read_only: a read-only synchronized editor is editable and its edits mutate the Emacs document
- **Category:** correctness-bug · **Verdict:** CONFIRMED · **Location:** `companion/app/src/main/kotlin/com/calebc42/ebp/companion/CoreRenderer.kt:90-112`
- The editor case reads only id/document/value and never consults read_only or enabled. For a synchronized editor (document non-empty) with read_only:true, the OutlinedTextField remains editable; each keystroke runs EditorSession.diff and calls bridge.editorEdit -> edit.delta, applying the change to the Emacs buffer the author marked read-only. Failure: Emacs sends {t:editor,id:doc1,document:notes.org,read_only:true,value:...}; user types a character; a splice is dispatched and the read-only document is silently mutated. This is a data-integrity break on an advertised node (editor is in the app profile's node_types).
- **Fix:** Honor read_only (and enabled): when read_only or enabled==false, render a non-editable/disabled field and suppress all edit.delta / state dispatch from the node.

### [SPEC 18.1 (para: 'Before completing dialog.submit ...')] dialog.submit skips the mandatory max_frame_bytes prospective-serialization check; oversized submit orphans the request and wedges the dialog
- **Category:** conformance-gap · **Verdict:** CONFIRMED · **Location:** `companion/wire/src/main/kotlin/com/calebc42/ebp/wire/CompanionEngine.kt:1365-1374`
- completeDialogSubmit does no size check. It removes the dialog from the map (line 1368) and then unconditionally respondResult(...)->emit->encodeFrame. encodeFrame (FrameCodec.kt:188) throws FrameClose when the body exceeds MAX_BODY_OCTETS. Reachable because dialog-captured field values have no per-field cap: a dialog may capture up to max_capture_fields (64) values, each an arbitrarily long text_input, so the fields object can exceed max_frame_bytes (4MB). Failure scenario: a dialog with several large text_inputs is submitted -> encodeFrame throws AFTER the dialog was removed and BEFORE dialogListener(id,null) at line 1373. Net effect: (a) the dialog IS completed/removed though the spec says it MUST NOT be; (b) the request id is never answered, so Emacs waits until its 3600s client timeout; (c) MainActivity.currentDialog is never cleared, so the modal stays on screen but a re-tap is a no-op (dialogs.remove returns null). No local diagnostic, values not kept, dialog not kept outstanding. Every clause of the MUST is violated.
- **Fix:** In completeDialogSubmit, build the prospective response, measure encodeFrame(result).size (or the UTF-8 body) against limits.max_frame_bytes BEFORE dialogs.remove; on overflow keep the dialog in the map, keep non-password values, surface a local diagnostic via dialogListener, erase any captured password per 14.6, and return without responding.

### [SPEC 18.6] Accepted reminder set is never persisted; ReminderStore is a per-connection in-memory field
- **Category:** conformance-gap · **Verdict:** CONFIRMED · **Location:** `companion/wire/src/main/kotlin/com/calebc42/ebp/wire/ReminderStore.kt:12-16; CompanionEngine.kt:793; companion/app/.../DeviceBridge.kt:192`
- SurfaceStore (FileSurfaceBacking) and DurableQueue (FileQueueStore) are constructed in DeviceBridge and passed into every engine so they outlive connections and restarts. `reminders` is instead a plain `val reminders = ReminderStore()` field inside CompanionEngine, and a fresh CompanionEngine is built per socket in serve() (DeviceBridge.kt:192). ReminderStore holds owners/fired in a LinkedHashMap/HashSet with no disk backing. Failure: Emacs sets a reminder for tomorrow then disconnects (the normal steady state). On device reboot the OS clears AlarmManager alarms; nothing durable holds the accepted set and nothing re-arms it, so the reminder never fires. Even on a mere reconnect the new engine's ReminderStore is empty, so the accepted set, its fired receipts, and max_reminders accounting are all gone.
- **Fix:** Give ReminderStore a file/SQLite backing (as SurfaceStore/DurableQueue have) and share one instance across connections via the engine constructor, so the accepted set and fired receipts survive process and device restarts.

### [SPEC 18.6] Fired state is not durable and the presentation path never records or consults a receipt
- **Category:** conformance-gap · **Verdict:** CONFIRMED · **Location:** `companion/wire/src/main/kotlin/com/calebc42/ebp/wire/ReminderStore.kt:16,51-59; companion/app/.../Notifications.kt:104-113`
- Fired receipts live in an in-memory HashSet (ReminderStore.kt:16) that is never persisted. Worse, the actual presenter — ReminderAlarmReceiver.onReceive — posts the notification directly and never calls markReminderFired/isFired; a grep confirms markFired/dispatchReminderTap have no production call sites (only unit tests). The receiver comment concedes at-most-once rests solely on 'the AlarmManager one-shot already fires once' and defers the receipt store. So fired state is neither persisted nor checked before presenting. Failure: process is killed and relaunched after an alarm fired but before dismissal, or the same tuple is re-armed (see next finding) — nothing durable records that (owner,id,at_ms) already fired, so it re-presents.
- **Fix:** Persist the fired receipt for (owner,id,at_ms) atomically before/with the notify() call inside the receiver's presentation path, and check it there; the wire-layer markFired must be reachable from the platform presenter.

### [SPEC 18.6] Re-pushing an unchanged/already-fired set re-arms the alarm and re-presents (double fire)
- **Category:** correctness-bug · **Verdict:** CONFIRMED · **Location:** `companion/app/.../Notifications.kt:46-60; companion/app/.../DeviceBridge.kt:217-219`
- reminderListener unconditionally calls scheduleReminders for the whole new set, and scheduleReminders arms an alarm for every reminder via setExactAndAllowWhileIdle with FLAG_UPDATE_CURRENT, ignoring fired state entirely (it never consults isFired). ReminderStore.replace() does preserve the wire receipt for an unchanged tuple, but that receipt is dropped on the floor by the platform arm path. Failure: an agenda app re-pushes its full reminder set every minute (a realistic pattern). A reminder whose at_ms has already passed and fired gets re-armed at that past RTC time; setExactAndAllowWhileIdle with a past trigger fires immediately, producing a second (and third, fourth...) presentation of an already-fired tuple — a direct at-most-once violation.
- **Fix:** Before arming, skip any tuple whose durable fired receipt is set; only (re)arm tuples that are new or whose at_ms changed.

### [SPEC 18.6] A reminder tap never enters the Section 14 pipeline; on_tap is unwired
- **Category:** deferral-risk · **Verdict:** CONFIRMED · **Location:** `companion/app/.../Notifications.kt:2-7,104-113`
- ReminderAlarmReceiver builds a Notification with no contentIntent, so tapping it only auto-cancels (setAutoCancel(!ongoing)=true) — it never reaches CompanionEngine.dispatchReminderTap, which is confirmed dead in production. The engine's dispatchReminderTap correctly injects owner/reminder_id and honors drop/queue/wake, but nothing invokes it. The file header explicitly defers 'routing a notification/reminder tap back to Emacs with its offline policy' as a follow-on. Failure: user taps a reminder carrying on_tap {action:'agenda.open', when_offline:'queue', ttl_s:3600} — no event.action is ever admitted or queued, so the authored action silently never runs. This MUST cannot be deferred and still conform.
- **Fix:** Attach a contentIntent that routes the tap (owner,id) to dispatchReminderTap on a live/queued path; wire dismissal-without-tap to NOT dispatch (already correct in the engine).

### [SPEC 18.6] No BootReceiver re-arms alarms after device restart (RECEIVE_BOOT_COMPLETED declared but unused)
- **Category:** conformance-gap · **Verdict:** CONFIRMED · **Location:** `companion/app/src/main/AndroidManifest.xml:10 (permission present); boot receiver MISSING`
- The manifest requests android.permission.RECEIVE_BOOT_COMPLETED but registers no receiver with a BOOT_COMPLETED intent-filter (only ReminderAlarmReceiver with no filter). Android clears all AlarmManager alarms across a reboot, so armed reminders are lost and, with no durable ReminderStore to reconstruct from (see finding 1), never re-scheduled. Failure: reminder armed for tomorrow 09:00; user reboots the phone tonight; at 09:00 nothing fires. The declared permission is dead weight without the receiver + a durable set to replay.
- **Fix:** Add a BOOT_COMPLETED (and TIMEZONE_CHANGED/TIME_SET) receiver that reloads the persisted accepted set and re-arms unfired reminders.

### [SPEC 21.1 / 21.2] Registrations and all runtime records are in-memory only — no persistence across restart
- **Category:** deferral-risk · **Verdict:** CONFIRMED · **Location:** `TriggerStore.kt:30 (byIdentity = LinkedHashMap, in-memory); TriggerStore.kt:20-27 (Registration runtime records are plain fields); comment TriggerStore.kt:8-9`
- TriggerStore holds byIdentity in a LinkedHashMap and every runtime record (throttleFloorMs, oneShotCompleted, scheduleAnchorMs, lastFireFloorMs, bootGeneration, baselines) is a non-persisted Registration field. On Companion/device restart the entire armed set and all throttle floors vanish. Failure scenario: a queue trigger with throttle_s=3600 fires, then the Companion process restarts 5s later; because throttleFloorMs was never durably committed, the very next observation re-admits the same trigger, producing an immediate duplicate the spec explicitly forbids. Also 'Removed IDs MUST NOT fire' and 'MUST persist across restarts' are both unmet. The code comments mark durable backing as deferred to a later atom, but atoms 11b-11d are marked completed and durability is still absent, so this deferral breaks 21.1/21.2 conformance now.
- **Fix:** Back TriggerStore and the Registration runtime records with the same durable store the queue/reminders use; commit throttle floor, one-shot/boot receipts, schedule anchors and baselines in the 21.2 transaction. Until then the triggers module cannot claim conformance.

### [SPEC 21.1 / 21.2] Trigger registrations and throttle state are in-memory per-connection: no persistence across restart
- **Category:** deferral-risk · **Verdict:** CONFIRMED · **Location:** `CompanionEngine.kt:883 (val triggers = TriggerStore()); TriggerStore.kt:30 (private byIdentity LinkedHashMap, no backing store); TriggerStore.kt:21 (throttleFloorMs held only on in-memory Registration)`
- Unlike `queue: DurableQueue` and `surfaces: SurfaceStore` (constructor-injected, durable, shared across connections), `triggers` is a bare in-memory TriggerStore constructed inline on each CompanionEngine, and every runtime record (throttle floor, baselines) lives only on the in-memory Registration. Failure scenario: register a battery-low queue trigger; kill/restart the Companion process; on the next connection the TriggerStore is empty, so the registration is gone entirely and never fires again (violating persist-across-restart). Even within one process, throttleFloorMs is never persisted, so a restart resets the throttle floor and the next crossing produces an immediate duplicate the throttle was meant to suppress. The source comment (TriggerStore.kt:8-9) and memory notes admit durable backing was deferred to W8, but the module is marked DONE and 21.1/21.2 make persistence a MUST now.
- **Fix:** Hoist TriggerStore out of CompanionEngine into a durable, identity-scoped backing store (mirroring QueueStore/SurfaceBacking), persisting registrations AND every runtime record (throttle floor, baselines, one-shot/boot/schedule markers) atomically; load and re-baseline on construction/restore.

### [SPEC 21.2 / 21.1] Firing is impossible while disconnected: every entrypoint early-returns without a live authenticated session
- **Category:** conformance-gap · **Verdict:** CONFIRMED · **Location:** `CompanionEngine.kt:929-931, 936-938, 943-949 (observeTriggerSample/observeTriggerEvent/fireManualTrigger each do `pendingPairingId ?: return` and require `"triggers" in granted`)`
- pendingPairingId is set only during the handshake and `granted` only in buildWelcome; both exist only for a live, authenticated, granted connection. So the firing runtime cannot be reached at all while the device is disconnected from Emacs. Failure scenario: phone is away from the paired Emacs (no session); battery crosses below 20% for a queue-policy trigger; the platform battery receiver calls observeTriggerSample, which returns immediately because pendingPairingId is null. Result: no durable queue admission, no throttle commit, no on_fire notification. The entire offline/bounded-response purpose of the trigger module (queue/wake events accumulated while disconnected, drop-policy on_fire fired locally while not READY) is non-functional. The correct behavior even for the no-session case is a device-lifetime firing service that commits throttle, runs on_fire, and admits durable queue/wake records independent of any connection.
- **Fix:** Make the firing runtime a device-lifetime service keyed by pairing identity, decoupled from connection/session lifecycle; observe* must admit durable events, commit throttle, and run on_fire regardless of whether a session exists, with remote delivery/on_fire drop-vs-durable decided by the trigger policy and current READY state.

### [SPEC 21.2] Five-step order inverted: on_fire runs and throttle is consumed BEFORE the durable event commit
- **Category:** correctness-bug · **Verdict:** CONFIRMED · **Location:** `TriggerRuntime.kt:174-187 (throttleFloorMs=now(); then the onFire loop; then emit(reg,data) last) with the durable commit occurring inside emit -> CompanionEngine.kt:954-979 (emitTriggerFired -> queue.admit)`
- tryAdmit performs: set throttle (in-memory) -> run on_fire entries -> emit (which is where queue.admit, the durable commit, actually happens). The SPEC order is commit-then-on_fire, with a hard rule that a failed durable transaction must not have executed local responses. Failure scenario: the durable queue is at max_queued_events (or a storage error occurs); a queue-policy trigger with on_fire:[{cap:vibrate}] is admitted. tryAdmit consumes the throttle and executes vibrate, THEN emitTriggerFired calls queue.admit which returns QueueFull/StorageFailed and the event is silently dropped (CompanionEngine.kt:978 `else -> Unit`). Net effect: the local response ran and the throttle floor was consumed even though the durable transaction failed and no remote event exists. This also means throttle state and the event record are not committed in one transaction (throttle lives on the Registration, the event in the queue), and on QueueFull the throttle-suppresses a later legitimate occurrence.
- **Fix:** Reorder tryAdmit to: evaluate gate+throttle -> freeze fire data + EventId -> durably commit {throttle floor, one-shot/boot receipt, and for queue/wake the event record+queue_seq} in one transaction -> only on success run on_fire -> make remote eligible. Roll back the throttle-floor consume if the durable commit fails.

### [SPEC 21.2 (steps 3-4), read together with 21.4] on_fire executes BEFORE the durable event-record commit; local responses run even when the durable transaction fails
- **Category:** correctness-bug · **Verdict:** CONFIRMED · **Location:** `TriggerRuntime.kt:181-187 (on_fire loop then emit) with the durable commit at CompanionEngine.kt:968 (queue.admit inside emitTriggerFired, invoked as emit(reg,data))`
- tryAdmit runs the full on_fire loop (Substitution.apply -> onFire) at lines 181-185 and only THEN calls emit(reg,data) at line 187, which is emitTriggerFired; that method is where queue.admit — the step-3 durable event-record commit — actually happens (CompanionEngine.kt:968). So for every `queue`/`wake` trigger, step 4 runs before step 3. Concrete failure: a `queue`-policy battery.level trigger with on_fire [{cap:"vibrate"}] crosses below its threshold while the durable queue is at max_queued_events (or the store errors). tryAdmit commits the throttle floor, runs on_fire -> the device physically vibrates via capabilityHandler, THEN emit->queue.admit returns AdmitResult.QueueFull/StorageFailed and the event is silently dropped (CompanionEngine.kt:978 `else -> Unit`). Result: the local response executed although the durable transaction did not commit and no remote event was admitted — a direct MUST violation. Second consequence (data-integrity): a crash in the window after the on_fire side effect but before queue.admit loses the remote event entirely while the local effect already happened, the reverse of the spec's commit-first ordering. Neither OnFireTest (emit = {_,_->}) nor TriggerRuntimeTest exercise on_fire against a real DurableQueue, so this ordering is untested.
- **Fix:** Reorder tryAdmit so the durable commit (throttle state + event record + queue_seq) is performed and confirmed Admitted BEFORE the on_fire loop runs; on QueueFull/StorageFailed, do not execute on_fire. For `drop`, keep on_fire best-effort after the throttle commit as today. Add a regression test that admits with a full/failing queue and asserts onFire was not invoked.

### [SPEC 18.6] Reminder at-most-once fired-state not persisted; markReminderFired is dead code and the alarm receiver presents unconditionally
- **Category:** conformance-gap · **Verdict:** CONFIRMED · **Location:** `ReminderStore.kt:16,51-53 (fired = HashSet, in-memory); CompanionEngine.kt:864 (markReminderFired never called from any presenter); Notifications.kt:104-113 (ReminderAlarmReceiver.onReceive posts without consulting fired-state)`
- The fired receipt lives in an in-memory HashSet, and the code that would record it (markReminderFired / ReminderStore.markFired) is never invoked by the presentation path — ReminderAlarmReceiver.onReceive posts the notification directly, with a comment openly deferring cross-restart dedup. So fired-state is neither consulted nor persisted. Failure scenario: reminder (owner,id,at_ms) fires and presents; transport drops; Emacs reconnects (new engine, empty fired set) and re-sends the identical set (an unchanged tuple, which SPEC says 'preserves fired state'); the fresh store has no receipt and PendingIntent.FLAG_UPDATE_CURRENT re-arms the same alarm, so the reminder presents a second time for the same tuple — a direct at-most-once violation. A process restart between at_ms schedule and fire has the same effect.
- **Fix:** Persist fired receipts durably in the (hoisted) ReminderStore and gate ReminderAlarmReceiver presentation on markReminderFired returning true, committing the receipt before/atomically with the notify().

### [SPEC 21.1] Trigger registrations are not persisted across Companion/device restart
- **Category:** conformance-gap · **Verdict:** CONFIRMED · **Location:** `TriggerStore.kt:20-30 (Registration + byIdentity, all in-memory); CompanionEngine.kt:883 (val triggers = TriggerStore()); DeviceBridge.kt:192 (new engine per serve())`
- TriggerStore keeps byIdentity -> registrations purely in RAM inside the per-connection engine, with no file backing (the class comment concedes 'durable backing ... lands with the firing runtime', which never arrived). Failure scenario: Emacs registers a battery.level below-20 queue trigger; Companion returns {count:1}. The app process restarts; the new engine's TriggerStore is empty, so the armed trigger no longer exists and a subsequent battery-low crossing neither fires nor queues. TriggerSources keeps feeding samples to a runtime whose store has zero registrations. The set is likewise lost on any SPEC 5.2 reconnect.
- **Fix:** Hoist TriggerStore to DeviceBridge and back it durably (records: normalized entry + runtime records) like FileQueueStore; reload and re-baseline-preserving on construction; restore before device sources begin admitting.

### [SPEC 21.1] Per-connection store reset defeats the unchanged-ID carry-forward MUST — every reconnect re-baselines, re-anchors, and re-arms
- **Category:** correctness-bug · **Verdict:** CONFIRMED · **Location:** `DeviceBridge.kt:192 (new TriggerStore per connection); TriggerStore.kt:47-56 (replace compares against old, always empty after reconnect); CompanionEngine.kt:1011-1014 (replace + armBaselines re-baseline fresh registrations)`
- The canonicalEquals carry-forward at TriggerStore.replace() only preserves records when a prior Registration for the id exists in the SAME store instance. Because each reconnect builds a fresh empty TriggerStore, `old[id]` is always null, so every re-registered id — even a byte-identical one — is treated as new and armBaselines re-establishes its silent baseline / schedule anchor. Failure scenario: Emacs has a time.every_s:3600 repeating trigger and a battery.level below-20 trigger armed; the transport drops (routine) and Emacs reconnects and re-sends the identical set. The new store re-baselines the battery side (any crossing in progress across the drop is lost) and re-anchors the repeating schedule (acceptance anchor and last-fire floor reset), producing a missed or shifted fire. This breaks the strongest 21.1 MUST NOT and happens on a normal live reconnection, not only on process restart.
- **Fix:** Share one TriggerStore across connections (hoist to DeviceBridge, injected) so unchanged-ID carry-forward survives reconnect, and persist the runtime records so it also survives restart.

### [SPEC 21.2] throttle_s floor is not persisted — a restart or reconnect produces an immediate duplicate fire
- **Category:** conformance-gap · **Verdict:** CONFIRMED · **Location:** `TriggerStore.kt:21 (throttleFloorMs: Long? in-memory var); TriggerRuntime.kt:169-174 (reads/writes reg.throttleFloorMs only in RAM)`
- The throttle floor is a var on the in-memory Registration with no durable write. Failure scenario: a trigger with throttle_s:3600 is admitted at T0 (throttleFloorMs=T0). The process restarts at T0+60s (or the connection re-establishes). The reconstructed/re-registered trigger has throttleFloorMs=null, so the same condition recurring at T0+120s is admitted immediately — well inside the 3600s window — the exact immediate duplicate this MUST forbids. The rollback-proof clock (queue.effectiveNow) is used while running, satisfying the wall-clock-rollback SHOULD, but nothing is persisted across restart.
- **Fix:** Persist throttleFloorMs (conservative wall time) as part of the durable registration record, committed in the same transaction as the occurrence per SPEC 21.2 step 3.

## P2 findings (33)

### [SPEC 4.5] SPEC 4.5 welcome reservation omits the device report from B — checkLimits can pass while the real welcome exceeds max_frame_bytes
- **Category:** conformance-gap · **Verdict:** PARTIAL · **Location:** `companion/wire/src/main/kotlin/com/calebc42/ebp/wire/CompanionEngine.kt:1522-1536 (prospective welcome) vs 1476-1477 (buildWelcome adds device)`
- checkLimits() builds the worst-case prospective welcome from server_proof/protocol/server/granted/surface_profiles/surfaces/queued_events/input_state/limits, but never adds the `device` member. buildWelcome() emits `device: config.deviceReport` whenever `capabilities` or `triggers` is granted. Because the reservation formula B + max_input_state_bytes - 2 <= max_frame_bytes is computed without the device report's bytes, a Companion that will grant triggers/capabilities and carries a large device report (many caps, permissions, trigger_types, state_types, trackable_state_types, trigger_caps) can pass the startup require() yet produce an authenticated welcome whose UTF-8 body exceeds max_frame_bytes. That welcome frame is then rejected by the peer decoder (body > max_body_bytes) and the session cannot authenticate. The spec explicitly names the device report as part of the reservation; the code's own comment brags about closing the identical hole for `surfaces`.
- **Fix:** In the prospective welcome, include `.put("device", config.deviceReport)` (or the maximal device report the Companion can report) whenever capabilities/triggers is in the supported set, so B accounts for it.

### [SPEC 23.3] Emacs endpoint logs full message bodies by default — auth proofs, clipboard, SMS bodies, call numbers, and private editor content all captured
- **Category:** security · **Verdict:** PARTIAL · **Location:** `/home/calebc42/pkb/projects/jetpacs/jetpacs/llm-poc-2/emacs/ebp.el:1266`
- ebp-connect creates the live `ebp--connection` (a jsonrpc-process-connection subclass) via make-instance with NO :events-buffer-config and no :events-buffer-scrollback-size. In the target runtime (GNU Emacs 30.1, /usr/share/emacs/30.1/lisp/jsonrpc.el.gz) the connection slot `-events-buffer-config` defaults to `(:size nil :format full)`, and jsonrpc--log-event (installed on jsonrpc-event-hook by default) logs when `(or (null max) (cl-plusp max))` — with :size nil it logs the FULL JSON body of every message, unbounded (the trim branch `(when max ...)` is skipped). Failure scenario: Emacs calls capability.invoke clipboard.read -> Companion replies {"text":"<clipboard/password>"}; the entire reply body is inserted verbatim into the `*ebp events*` buffer. The same buffer captures welcome.server_proof and auth.response.client_proof (authentication proofs), trigger.fired args.data.body / args.data.number (SMS bodies, call numbers), and edit.open/edit.delta `text` (private editor content) — every category §23.3 names as MUST-NOT-log, retained by default with no opt-in and no size cap. This is the exact inverse of §23.3's 'enable detailed payload logging only through an explicit developer setting'.
- **Fix:** Pass `:events-buffer-config '(:size 0)` (disables logging) when constructing ebp--connection, and gate full-body logging behind an explicit ebp developer variable. Amendment #34 blesses jsonrpc.el for transport/framing/id bookkeeping only — it does not exempt its default diagnostic buffer from §23.3.

### [SPEC 18.6] Accepted reminder set is not persisted across process/device restart (in-memory, per-connection store)
- **Category:** conformance-gap · **Verdict:** PARTIAL · **Location:** `ReminderStore.kt:12-16 (LinkedHashMap/HashSet, no backing); CompanionEngine.kt:793 (val reminders = ReminderStore()); DeviceBridge.kt:192 (new CompanionEngine per serve())`
- ReminderStore holds owners/fired entirely in RAM and is constructed fresh inside each CompanionEngine, which DeviceBridge.serve() creates per TCP connection (contrast the shared file-backed store/queue injected at DeviceBridge.kt:48,51). Failure scenario: Emacs sends reminders.set with a reminder for tomorrow; Companion returns {count:1}; the app process is killed or the device reboots. On restart a new engine builds an empty ReminderStore, so the accepted set is gone; the platform alarm is also lost on device reboot (ReminderAlarmReceiver has no BOOT_COMPLETED re-arm), so the reminder never presents. Even without a restart, a routine SPEC 5.2 reconnect (new socket -> new engine) wipes the set mid-day.
- **Fix:** Hoist ReminderStore to a DeviceBridge field injected into the engine, and give it durable file backing modeled on FileQueueStore/QueueStore (write-temp+fsync+atomic-rename), loaded at construction; re-arm alarms from the persisted set on boot.

### [SPEC 4.5 (lines 261-284)] checkLimits omits the device report from the §4.5 reservation body B while buildWelcome emits it
- **Category:** conformance-gap · **Verdict:** PARTIAL · **Location:** `companion/wire/src/main/kotlin/com/calebc42/ebp/wire/CompanionEngine.kt:1522-1536 (prospective body; no `.put("device",...)`); emitted at :1476-1477`

- handleDialogShow reads only dialog_id and spec; `style` is never read, validated, or forwarded to the renderer, and RenderDialogRoot always presents a modal Dialog. An out-of-vocabulary style (e.g. "sheet_half") is silently accepted rather than rejected, and `sheet`/`sheet_full` presentation is not implemented. The SPEC does not explicitly state whether an unknown style MUST be 1201, so this is partly a spec hole worth an amendment pinning the rejection rule; the contract already lists dialog.style as a closed vocabulary.
- **Fix:** Validate `style` against {dialog,sheet,sheet_full} (1201 otherwise) and pass it to the renderer; amend 18.1 to state that an unknown style is content-invalid.

### [contract.json methods.pie_menu.show/dismiss states:["READY"]; SPEC 18.3] pie_menu.show/dismiss are processed outside the READY state the contract requires
- **Category:** edge-case · **Verdict:** CONFIRMED · **Location:** `companion/wire/src/main/kotlin/com/calebc42/ebp/wire/CompanionEngine.kt:615-640 (handleNotification)`
- handleNotification only drops notifications in CONNECTED/CHALLENGED (line 618); it never consults the per-method `states`. pie_menu.show/dismiss are declared READY-only in the contract, yet a pie_menu.show arriving in SYNCING is dispatched and a menu is shown. This is generic to all READY-only notifications (theme.set is legitimately SYNCING+READY), but for pie menus it lets a menu exist before the session is READY. Failure: an authenticated peer sends pie_menu.show during SYNCING and the Companion presents the menu though the state is not yet READY.
- **Fix:** Gate notification dispatch on METHOD_REGISTRY[method].states containing the current SessionState (drop otherwise), so READY-only notifications are ignored in SYNCING.

### [SPEC 14.1] capture_fields on a notification on_tap is not resolved or rejected
- **Category:** conformance-gap · **Verdict:** CONFIRMED · **Location:** `companion/wire/src/main/kotlin/com/calebc42/ebp/wire/SpecValidator.kt:218`
- validateNotificationAction rejects capture_fields only when `input` is present (line 218). A non-input action `on_tap:{action:"a.b",capture_fields:["ghost"]}` is accepted even though the notification body advertises no stateful nodes, so `ghost` can never resolve. The canonical validateAction defers and resolves every capture name via ctx.captureRefs; the notification path never does. Failure: the surface is applied instead of returning 1201 content-invalid for an unresolved capture name.

### [SPEC 18.5 / 4.2] chronometer.base_ms accepted as any number, not a non-negative integer timestamp
- **Category:** edge-case · **Verdict:** CONFIRMED · **Location:** `companion/wire/src/main/kotlin/com/calebc42/ebp/wire/SpecValidator.kt:172`
- The check is only `chrono.opt("base_ms") !is Number`. base_ms:-1, base_ms:1.5, or base_ms:1e400 (infinite) are accepted. Section 4.2 requires a non-negative integer. Low impact today because postSurface ignores chronometer, but it is an accepted-invalid content case.
- **Fix:** Validate base_ms is an integral, finite, non-negative safe integer (as ttl_s is validated at lines 423-428).

### [SPEC 4.4 (via SPEC 18.6 'non-empty identifier' / 'id | identifier')] owner and reminder id length is not bounded to 128 ASCII characters
- **Category:** conformance-gap · **Verdict:** CONFIRMED · **Location:** `companion/wire/src/main/kotlin/com/calebc42/ebp/wire/CompanionEngine.kt:799,807,837`
- The identifier regex [A-Za-z0-9][A-Za-z0-9._:/-]* used for both owner (line 807) and reminder id (line 837) is anchored via matches() but has no upper length bound, so identifiers over 128 chars are accepted where §4.4 requires rejection. Failure: owner or id of 500 characters passes validation and is stored/keyed. Impact is bounded by max_body_bytes so it is minor, but a conforming receiver MUST reject over-length identifiers.
- **Fix:** Enforce the 1..128 ASCII-octet identifier bound (max_identifier_bytes) on owner and reminder id.

### [SPEC 4.2 / 18.6 (at_ms is a timestamp)] Fractional at_ms is truncated rather than rejected
- **Category:** edge-case · **Verdict:** CONFIRMED · **Location:** `companion/wire/src/main/kotlin/com/calebc42/ebp/wire/CompanionEngine.kt:844-846`
- validateReminder accepts any Number for at_ms and calls toLong(). A JSON number with a fractional part (e.g. 1784700000000.9) satisfies `at is Number` and is silently truncated to 1784700000000 rather than rejected, contradicting the integer-milliseconds definition of a *_ms timestamp. Failure: at_ms:1784700000000.9 is accepted and schedules at the floored millisecond. Minor, but a strict receiver should reject a non-integer timestamp.
- **Fix:** Reject at_ms whose numeric value is not an integer (e.g., Double with a fractional component) in addition to the existing range check.

### [contract.json methods.edit.apply (params.required)] Text-changing edit.apply does not reject a missing REQUIRED cursor
- **Category:** conformance-gap · **Verdict:** CONFIRMED · **Location:** `companion/wire/src/main/kotlin/com/calebc42/ebp/wire/CompanionEngine.kt:1173-1190`
- The text-changing branch null-checks seq/start/del/text/len but not cursor; `cursor` is applied only via `(params.opt("cursor") as? Number)?.toInt()?.let { ... }`. Failure scenario: an edit.apply that omits the REQUIRED `cursor` (or sends it non-numeric) still applies the splice and returns {status:'applied'}, leaving cursor at the splice-derived default rather than being rejected with -32602. Minor because the splice result is still correct, but a REQUIRED member is silently tolerated.
- **Fix:** Include `cursor` in the -32602 guard for the text-changing form (parse it as a required Number), consistent with the move-only branch which already rejects a missing cursor.

### [SPEC 20.3] Elisp caller does not validate the capability Result shape (closed-result MUST)
- **Category:** conformance-gap · **Verdict:** CONFIRMED · **Location:** `emacs/ebp.el:1187`
- ebp-client-capability-invoke forwards the raw jsonrpc result plist straight to the application callback with no check that it is the exact closed catalog Result (no implementation-private members, correct members for the invoked cap). If a Companion returned an invalid Result (extra member, wrong shape), the caller would not 'fail its local invocation' or emit a safe log.error as required. Low practical risk (Emacs dials only its authenticated, conformant Companion, and amendment #34 makes the Emacs endpoint RECOMMENDED-strict on framing) — but the §20.3 result-shape MUST is caller-side and not carved out by #34.
- **Fix:** Validate the returned result against the catalog row for `cap` (closed member set) before invoking the callback; on mismatch, deliver an error to the callback and send one log.error.

### [SPEC 20.2] Explicit `args: null` is coerced to {} rather than rejected as -32602 on the adversarial Companion side
- **Category:** edge-case · **Verdict:** CONFIRMED · **Location:** `companion/wire/src/main/kotlin/com/calebc42/ebp/wire/CompanionEngine.kt:1042`
- handleCapabilityInvoke treats both absent args and an explicit JSONObject.NULL as {}. `args` defaults to {} only when *absent*; an explicit `"args": null` is a present member whose value is not an object. Failure: {cap:"clipboard.read", args:null} is coerced to {} and executes, rather than -32602. This is a lenient acceptance of a malformed member on the strict-receiver (Companion) side per §6.2; harmless for the reference but inconsistent with the closed-Args discipline.
- **Fix:** Treat a present non-object args (including null) as -32602; default only when the member is absent.

### [SPEC 21.2 / 14.4] Oversized trigger event is dropped after throttle+on_fire already ran, with no local diagnostic
- **Category:** edge-case · **Verdict:** PARTIAL · **Location:** `CompanionEngine.kt:965-966 (emitTriggerFired: `if (params...size > max_event_bytes) return`), reached only after TriggerRuntime.kt:174-185 has consumed throttle and executed on_fire`
- The max_event_bytes check in emitTriggerFired runs after tryAdmit has consumed the throttle floor and executed on_fire, and returns silently with no log.error diagnostic. Failure scenario: a trigger whose substituted fire data pushes the trigger.fired params past max_event_bytes -> throttle consumed, on_fire executed, remote event silently discarded, no diagnostic emitted (unlike dispatchAction which returns a 1201 event-too-large). Largely a symptom of the same ordering defect as the P1 five-step finding.
- **Fix:** Perform the size/eligibility check as part of the pre-commit step (before on_fire and throttle consume), and emit a rate-limited local diagnostic on drop.

## Cross-cutting themes

- Durable/offline persistence is the single dominant defect: reminders (18.6) and triggers (21.1/21.2/21.5) keep all state in per-connection in-memory maps (ReminderStore, TriggerStore) while the codebase already file-backs SurfaceStore/DurableQueue and injects them via DeviceBridge. One architectural fix — hoist both stores to DeviceBridge with durable backing shared across connections — closes ~10 MUST violations spanning both modules and the cross-cut.
- Connection-scoped engine lifecycle amplifies (1): DeviceBridge.serve() mints a fresh CompanionEngine per socket, so any state not constructor-injected is wiped on a routine SPEC 5.2 reconnect, not merely a restart. This is what turns the durability gap into a carry-forward/re-baseline correctness bug and a throttle-reset duplicate-fire.
- Android platform-presentation layer lags the wire layer: the engine correctly parses/validates/forwards theme colors+syntax, notification meta.actions, reminder taps/cancels/receipts, and editor read_only/inbound edits, but the app host (DeviceBridge/MainActivity/Notifications/CoreRenderer) discards them — a systemic host-side wiring debt rather than isolated bugs.
- Validator-completeness: notification on_tap (18.5), pie descriptors (18.3), dialog remote actions (18.1), and slider/enum/toolbar (17.4/17.7) each hand-roll a subset of the canonical validateAction, so §14.1/§16.1 MUST-reject rules (unknown builtin, ttl_s range, drop+ttl_s/dedupe conflict, dotless action name, capture-field resolution, exactly-one action/builtin) are skipped on those paths. Fix pattern: delegate every on_tap to validateAction with an appropriate Ctx.
- Identifier §4.4 128-octet length cap is enforced for node/surface/server ids (SpecValidator/SurfaceStore/FrameCodec.MAX_IDENTIFIER_OCTETS) but the shared regex lacks a length bound and is applied bare to trigger id/dedupe, pie menu_id, and reminder owner/id — three modules missing the same cap.
- SPEC 4.5 welcome reservation omits the device report: checkLimits builds prospective B without the `device` member that buildWelcome emits when capabilities/triggers is granted — a soundness hole in the same reservation the author already patched for `surfaces`. Latent today (device report is a fixed ~200 bytes) but formally non-conformant and compounded by the absence of any reported size bound on the device report.
- Notification state-legality gate missing: handleNotification never checks spec.states, so READY-only notifications (toast.show, pie_menu.show/dismiss, diagnostics/eldoc/fontify) are processed during SYNCING — the notification analogue of handleRequest's 1204 guard is simply absent.
- Firing-runtime atomicity/ordering: on_fire and throttle are committed outside the durable transaction (21.2/21.4), and one-shot completed / boot generation / schedule-anchor fields are declared but never read or written, so at-most-once and coalescing MUSTs are unmet across the trigger firing surface.
- Latent security surface gated only by the reference advertising battery.level: hardcoded SPEC 9.3 KAT pairing with no release-build guard, on_fire lock-screen concealment, keystore encryption of queued sensitive payloads, and per-source-to-sink approval granularity all break the moment sms/call/calendar is advertised or the app ships — plus the always-on Emacs full-body logging (the one currently-reachable item).
- Non-issues worth stating to prevent false positives: the DEFERRED capability catalog rows (settings.open, intent.*, app.launch, apps.list, shortcuts, state.get, trigger.fire) are NOT advertised (device.caps = [vibrate, clipboard.read]); since only an advertised row is normative, deferring them is conformant now. Amendments 34-39 are largely outside these modules; only #37 (toolbar line-ops, unvalidated/unrendered) and #39 (surfaces.tile, unimplemented) intersect W7.

## Amendment recommendations

- SPEC 20.1 + 4.5: Introduce a reported max_device_report_bytes limit (or bound each device-report member) and state that the §4.5 welcome reservation MUST count the complete device report at that bound. Today the spec says the reservation 'covers the complete device report' and must use 'the largest state the implementation can report,' but with no numeric bound the guarantee that an authenticated welcome always fits max_frame_bytes is unprovable at the wire — flagged by two independent findings.
- SPEC 18.1: Pin the handling of an unrecognized dialog.style value. §12 rule 6 requires a closed-vocabulary member to define either a safe fallback or whole-object rejection, and contract.json makes dialog.style a closed vocabulary, yet 18.1 defines neither. Recommend explicit text: an unknown style falls back to `dialog` (consistent with text.style's documented body-fallback), or otherwise 1201 content-invalid.
- SPEC 21.4: Clarify that the source-to-sink substitution approval is represented and enforced per (sensitive-source-type, sink-kind) combination, not as a single blanket allowance. The current wording ('approval of that source-to-sink combination') already implies this, but an explicit note that a single global boolean is non-conformant would prevent the under-enforcement the reference exhibits and guide implementers toward a set-of-approved-pairs model with default-deny.
- SPEC 18.6 (guidance, optional): Add a non-normative implementation note that 'persist the accepted set across device restarts' plus platform alarm re-arming requires a boot-completed re-arm path where the platform clears scheduled alarms on reboot — several findings show implementers reading the MUST as satisfied by a durable store alone while the OS-cleared alarms are never re-armed.

Amendments 34-39 do not touch this cross-cut and need no change here; the elisp endpoint is the sender and is not where these persistence MUSTs live.
- **SPEC 4.5 welcome-size reservation × SPEC 20.1 device report (CompanionEngine.checkLimits / buildWelcome)** — Non-conformant: buildWelcome emits a variable-size `device` report that checkLimits never counts in the §4.5 reservation `B`, so the reservation can pass at startup while the emitted authenticated welcome busts max_frame_bytes and encodeFrame closes the connection; the spec compounds this by defining no reported bound (max_device_report_bytes) on the device report, so "the largest state the implementation can report" is unenforceable at the wire.
