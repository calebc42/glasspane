## §1 A8-1 — the blocking send runs timers, and dispatch re-enters

### 1.1 The mechanism — CONFIRMED end to end

Every hop pinned at the tag:

1. `process.c:3700` — network fds are non-blocking.
2. `process.c:6644` `send_process`. On `EWOULDBLOCK` (`:6850`) it pushes the unwritten remainder to
   the **front** of `p->write_queue`, then at `:6851`:
   ```c
   wait_reading_process_output (0, 20 * 1000 * 1000, 0, 0, Qnil, NULL, 0);
   ```
3. `process.c:5276` `wait_reading_process_output`. Its timer block (`:5426-5443`) is gated on
   ```c
   if (NILP (wait_for_cell) && just_wait_proc >= 0)
     { ... timer_delay = timer_check (); ... }
   ```
   `send_process` passes `wait_for_cell = Qnil` and `just_wait_proc = 0`, so **both conditions hold
   and `timer_check ()` runs arbitrary Lisp inside the send.**
4. `keyboard.c:4780-4805` `timer_check_2` calls `timer-event-handler` with **no global recursion
   guard** — the only interlock is the per-timer triggered slot (`ASET (chosen_timer, 0, Qt)`) — and
   with `specbind (Qinhibit_quit, Qt)`.
5. `jsonrpc.el:804-811` — the filter builds ordinary `timer-list` entries whose function is
   `jsonrpc-connection-receive`, and activates them.

**So jsonrpc.el's deferral does not deliver the property it was written to deliver.** Its own comment
at `:793-796` says the point is to "do this all this processing in **top-level loops timer**" — and
`send_process` runs timers, so "top level" is not where they land.

The bug#60088 guard (`jsonrpc--in-process-filter`, `:704-719`) does **not** cover this path: it
guards *filter → send*, and this is *send → filter*.

### 1.2 Reproduced, through the real stack

A server accepts, reads six notifications' worth, then goes deaf; the client issues one
`jsonrpc-notify` carrying a 48 MiB blob. **All six inbound notifications dispatched at t+0.533 s;
`jsonrpc-notify` returned at t+25.1 s.** Six of six dispatches ran inside our own half-written frame,
with `jsonrpc--in-process-filter` `nil` every time.

### 1.3 Byte interleaving is IMPOSSIBLE — the scarier reading REFUTED

Worth stating precisely, because it sets the severity. `write_queue_push` (`:6582`) appends with
`nconc2` when `front` is false and conses onto the head when true; `write_queue_pop` (`:6612`) always
takes the head. And `send_process`'s own head (`:6752-6754`):

```c
/* If there is already data in the write_queue, put the new data
   in the back of queue.  Otherwise, ignore it.  */
if (!NILP (p->write_queue))
  write_queue_push (p, object, buf, len, 0);
```

A nested send therefore appends to the **tail** and then drains from the **head** — writing the outer
frame's remainder first and its own bytes after. The queue is strict FIFO. Measured: `OUTERTAIL` then
`NESTEDMSG`, 67,108,891 bytes exactly, no loss or duplication.

**The hazard is re-entrant Lisp dispatch, not wire corruption.** Framing integrity and frame ordering
hold.

### 1.4 Two properties that change the picture

- **Nesting is unbounded, and completion is LIFO.** Twelve one-shot timers (jsonrpc's exact shape)
  during one send entered at depths 1→12 and **exited in strict reverse order**. Outbound bytes stayed
  FIFO. So the wire is FIFO while handler *completion* is LIFO.
- **Timer errors are swallowed** (`timer.el:331-341`). Any corruption caused by re-entrancy is silent.

### 1.5 The scenario is reachable by design on our own Companion

Not an attack — ordinary operation. `DeviceBridge.kt:423-431`:

```kotlin
while (engine.state != SessionState.CLOSED) {
    val n = input.read(buffer)
    if (n < 0) break
    engine.feed(buffer.copyOf(n))     // full decode + validate + dispatch, SYNCHRONOUS
}
```

`engine.feed` (`CompanionEngine.kt:105-130`) decodes, validates and dispatches on the **reader
thread**. While it validates a snapshot (up to 10,000 nodes) nobody is draining the socket, so:

1. Emacs sends a large `surface.update` (up to `max_frame_bytes` = 4 MiB);
2. the Companion is inside `feed()` for the previous frame, its receive buffer fills, then Emacs's
   send buffer fills;
3. Emacs blocks → §1.1 → our dispatcher runs inside our own half-written frame.

The Companion's single reader thread is *correct* — it is what buys §7.4's in-order dispatch. **The
Companion's ordering guarantee is what creates the Emacs endpoint's re-entrancy exposure.**

**The sharpest constraint on any remedy:** the sink writes from that same reader thread
(`DeviceBridge.kt:331-341`), so if Emacs stops reading, the Companion blocks in `out.write` and stops
reading too. Emacs's reading *inside* its blocked send is what breaks that cycle — **the re-entrancy
is the deadlock-avoidance mechanism**. Any remedy that suppresses inbound processing during a send
must not reintroduce the deadlock.

### 1.6 Exposure in `ebp.el`

`ebp.el` uses only `jsonrpc-async-request` / `jsonrpc-notify` — no synchronous request, no
`accept-process-output` — so the blocking send is the *only* re-entrancy source.

| | Finding | Status |
|---|---|---|
| **H1** | `ebp-client-surface-update` recorded `reset_input_ids` **after** the send. A re-entrant `state.changed` consults `reset-history` (`:1142-1148`) before the reset is recorded and adopts a draft the snapshot supersedes (§14.6 / P1 #2). The same function already hoists the *revision* claim correctly (`:1351-1353`). | **CONFIRMED, FIXED** (§8) |
| H2 | `ebp-client-edit-apply` reads `ed`/`old`/`seq`, sends, then writes `ed` in the callback from the pre-send read; a re-entrant `edit.delta` is clobbered. | CONFIRMED as a shape; wire outcome UNVERIFIED |
| H3 | `jsonrpc.el:305`/`:317` reply *after* the dispatcher returns, so under §1.4's LIFO nesting `event.action` replies leave in reverse receive order — what §7.4:684-686 forbids. | CONFIRMED; **not fixable in our code** without an outbound queue (R4) |
| H4 | `:858` enters `syncing` before the step-3 pushes at `:861-863`. | **Downgraded** — §10.3 requires SYNCING for those pushes, and `state.changed` is READY-only, so a conforming Companion cannot race it here. Not a defect. |

**Provably safe, recorded so nobody re-opens them:** outbound byte ordering; request-id allocation
(`ebp.el:751` vs `jsonrpc.el:882` — no yield between); surface revision monotonicity; handshake
fail-closed (send-then-step means a pre-auth state answers `1200`).

**Observation, not a defect:** `ebp-client--notification-dispatcher` (`:991-1002`) gates only on
`authenticated-p` = `(syncing ready)`, while §10.3 makes `state.changed` legal only in `READY`.
Accepting it early is lenient rather than wrong, and it is what defangs H4.

### 1.7 Candidates — **CANDIDATE, NOT RATIFIED**

| # | Kind | Shape | Honest limit |
|---|---|---|---|
| R1 | impl | Hoist every pre-send state claim above the send; recompute in-callback where the value is read back. | Fixes what is provable (H1 done, H2 outstanding). Cheapest. |
| R3 | SPEC | Name **"in transmission"** as a third state in §22.2 (see §2); add a §7.4 note that a send is not atomic w.r.t. the sender's own state; add re-entrant **depth** to §22.3's bounded resources. | Names the hazard; does not remove it. |
| R2 | impl | A bug#60088-style deferral guard in our dispatchers. | **Notifications only** — a request cannot defer, because `jsonrpc.el:317` replies with the dispatcher's return value. |
| R4 | impl | Our own outbound queue, so `process-send-string` is never called with more than the socket will take. | Most complete, most work; trades backpressure for queue growth. The only thing that would fix H3. |

Suggested order **R1 → R3 → R2 → R4**.

**UNVERIFIED and worth settling before R4:** on-device socket buffer sizes. §4.5's 4 MiB body cap is
the same order as one socket buffer, so a single maximum-size frame may block on Android — that sets
how often this is reachable in practice.

## §2 A8-1 corollary — §22.2 has no name for a half-written frame

Plan §7 predicted this would fold in, and it does. §22.2 partitions load-managed traffic into
"snapshots **waiting locally to be sent**" (conflatable) and a request "**already transmitted**"
(which "MUST NOT be discarded without concluding its local caller"). §1.3's measurement shows a third
state the partition has no name for: 64 MiB in the kernel with the tail still in `write_queue` —
irrevocably in transmission, yet concluding no caller.

The practical resolution is small: on any real host the handoff to the transport is the irrevocable
moment, so the conflation boundary is **the handoff, not the completion**. A sender can conflate
before `process-send-string`; after it, nothing can be retracted. §22.2 should say so.

## §3 A8-2 — unbounded number literal: mechanism real, deployment premise false

### 3.1 The mechanism — CONFIRMED, including the cross-check that was expected to refute it

Emacs 30.1 has a native hand-written JSON parser (no jansson). `json_parse_number` is at
`src/json.c:1277`; the digit loop at **`json.c:1311-1325`** terminates only on EOF or a non-digit —
**no digit cap**. Word overflow only sets a flag (`:1322-1323`), routing to `json_create_integer` →
`string_to_number` (`:1251`) → `bignum.c:433` `make_bignum_str` → `mpz_set_str`.

`mini-gmp.c:1390-1402` (`mpn_set_str_other`) is exactly as cited: `mpn_mul_1` over the whole growing
accumulator per chunk, i.e. Θ(n²). `maybe_quit` count is **0** across `mini-gmp.c`, `bignum.c` and
`json.c`.

**The expected refutation fails.** `integer-width` (65536 bits, `bignum.c:55`) is enforced only in
`make_bignum_bits` (`:99-100`), reached from `make_bignum`/`make_integer_mpz` — *arithmetic results*.
Literal reading goes through `make_bignum_str` (`:433-442`), which never touches that check; the
comment at `:296` confirms the split. Live: `(expt 10 100000)` signals `overflow-error`, while
`json-parse-string` happily returns a 100,000-digit bignum. **`integer-width` does not bound the JSON
path.**

### 3.2 Measured

The local Emacs **has libgmp**, so its timings measure the fast path: 4 M digits = **0.119 s**. To get
real mini-gmp numbers, `lib/mini-gmp.c` was compiled from the tag standalone: **exactly quadratic**,
constant 2.8e-12 s/digit² flat from 10 k→4 M, 4× per doubling, **4 M digits = 45.3 s** on an x86-64
desktop — and a 4 M-digit integer is inside every §4.5 limit.

Interruptibility is source-conclusive (no quit check exists). Note this composes with §1: timers run
with `specbind (Qinhibit_quit, Qt)` and `send_process` passes `read_kbd = 0`, so work reached from
that path is not user-interruptible either.

### 3.3 Why the impact collapses — deployment premise REFUTED

`configure.ac:7410-7439` and `java/INSTALL` do show libgmp on Android is an optional NDK side-port, so
a bare configure falls back to mini-gmp. **But the APK actually in use ships real libgmp**:
`emacs-30.2-29-arm64-v8a.apk` contains `lib/arm64-v8a/libgmp_emacs.so`, lists it `DT_NEEDED` in
`libemacs.so`, and imports `__gmpz_set_str`/`__gmpz_init` — real GMP's symbol prefix (a mini-gmp build
defines `mpz_set_str` internally with no such import).

Caveats stated honestly: nothing in-repo documents how Emacs reaches the device, and that APK is
**30.2**, not 30.1. So the hazard is real for a *self-built* Emacs without libgmp and absent from the
deployment we actually target.

**Corollary worth carrying (not part of A8, flagged for whoever owns §9):** the same APK also ships
`libgnutls_emacs.so`. The "Android has no GnuTLS" premise behind A7's pure-elisp HMAC reasoning may
not hold for this build either. Worth re-checking before that reasoning is relied on again.

### 3.4 The differential — one live defect

| Implementation | Behaviour |
|---|---|
| **Emacs** (`ebp.el:140-159` `ebp--check-numbers`) | Conformant — rejects out-of-safe-range integers, though *after* conversion, so it pays the cost it then refuses. |
| **Kotlin** (`EbpJson.kt:277-285`) | **Safe by construction** — `toLongOrNull`, never materializes a BigInteger; frame capped from the declared Content-Length at `FrameCodec.kt:172`. No change needed. |
| **Python** (`validate.py`) | **Live defect** — reproduced and **fixed** (§8). |

### 3.5 The spec gap

§4.2 requires rejecting an out-of-safe-range integral literal but never says the rejection must
*precede conversion*; §4.5's limits are per-body, per-field and per-depth with **no per-literal row**;
no digit-count or literal-length text exists anywhere in SPEC.md. §4.5's depth rule — the rejection
"MUST be made before the body is otherwise parsed, in bounded stack" — is the exact missing precedent.
§23.5's "MUST enforce Section 4 limits before allocating proportional resources" is partial cover but
not actionable, since §4.2 bounds the *value*, not the digit count.

### 3.6 Candidates — **CANDIDATE, NOT RATIFIED**

| # | Shape | Trade-off |
|---|---|---|
| C1 | Digit-count rule in §4.2 mirroring §4.5's bounded-stack clause (N = 17 falls out of the 2^53 boundary). | Emacs would need an elisp pre-scan and would likely inherit §4.5's RECOMMENDED-for-Emacs carve-out. |
| C2 | A `max_number_literal_bytes` row in §4.5, enforced in the linear pre-scan that already does depth. Fixed constant, not a negotiated `limits` member. | One more constant; reuses an existing scan. |
| C3 | Fix Python only; note the mini-gmp hazard informatively in §23.5. | Correctly sized to measured risk; leaves a self-built non-libgmp Emacs exposed. |

The Python fix is worth doing under any option, and is done (§8).

## §4 A8-3 — transport coding system: the stated hazard is not the real one

### 4.1 The base claims — CONFIRMED, with two corrections

`lisp/jsonrpc.el` @ emacs-30.1 (Version 1.0.25, `:7`) contains **zero** occurrences of
`set-process-coding-system` and **zero** of `:coding`. Its three process-creation sites (`:1124`,
`:1146`, `:1161`) are a throwaway port probe, the inferior program, and a caller-args
`open-network-stream` — none is the RPC stream. Per `:504-513` the stream process is supplied *by the
client*, so pinning is structurally the renter's job. The library is not negligent; it has no process
to pin.

**Correction 1.** `eglot.el:1590`'s `:coding 'utf-8-emacs-unix` is exact but it is the **pipe** path;
eglot's *network* path (`:1557`) is unpinned. Eglot is not the clean precedent the item assumed — we
pin what eglot leaves bare.

**Correction 2 (the important one).** The plan names `undecided-unix` as the dangerous resolution. It
is benign. Measured over a real loopback socket with live `jsonrpc.el`, one framed notification each:

| `:coding` | resolved to | dispatched? |
|---|---|---|
| `utf-8-unix` | `(utf-8-unix . utf-8-unix)` | **yes** |
| `undecided` | `(undecided-dos . undecided)` | **NO — silent permanent hang** |
| `undecided-unix` | `(undecided-unix . undecided-unix)` | yes |
| `binary` | `(binary . binary)` | yes (ASCII body; fails on non-ASCII) |

The hazard is **bare `undecided`**, which latches `-dos`, strips the CR from `\r\n\r\n`, and
jsonrpc.el's header search (`:740-744`, literal CRLF) then never fires. No error, no close, no
diagnostic. **That is already non-conformant** under A0/amendment **#91**, which put in §6.2 that a
role excused from strictness "MUST reach close, discard, or a documented tolerance … an unbounded
stall is not a conforming alternative." What is missing is not an obligation but a rule that would
have prevented an endpoint from getting there.

### 4.2 The framing-desynchronization hypothesis — REFUTED, structurally

The sharper hypothesis: `jsonrpc--connection-send` (`:575-583`) computes `Content-Length` as
`(string-bytes json)`, and `string-bytes` is `SBYTES` — the **internal** representation length
(`src/fns.c:265-272`) — not the coding-system-encoded length. If those can differ, the declared length
mismatches the octets written and the stream is corrupted from that point on.

They can differ, but cannot reach the wire. Two independent containments:

**Containment 1 — the divergent classes are rejected before serialization.** The divergence class is
exactly one: raw-byte characters `#x3FFF80..#x3FFFFF`, 2 internal bytes vs 1 wire octet. Lone
surrogates and above-Unicode code points give *invalid UTF-8* but **no** length divergence. Emacs
30.1's `json-serialize` rejects all of them loudly:

```
3FFF80 => (wrong-type-argument json-value-p "\200")
D800   => (wrong-type-argument json-value-p "\355\240\200")
110000 => (wrong-type-argument json-value-p "\364\220\200\200")
```

— §4.1's Unicode-scalar-value rule enforced by the host library for free.

**Containment 2 — `json-serialize` returns a UNIBYTE string.** Decisive, and not anticipated:

```
$ emacs -Q --batch --eval '(let* ((json (json-serialize (list :a "café𝄞"))))
    (princ (format "multibyte-p=%S length=%d string-bytes=%d utf8len=%d equal-to-encode=%S\n"
      (multibyte-string-p json) (length json) (string-bytes json)
      (length (encode-coding-string json (quote utf-8-unix)))
      (equal json (encode-coding-string json (quote utf-8-unix))))))'
multibyte-p=nil length=17 string-bytes=17 utf8len=17 equal-to-encode=t
```

For a unibyte string `string-bytes` **is** the octet count by construction, and encoding it is the
identity. `Content-Length` is correct *independently of the process coding system*.

This also explains the table above: the frame handed to `process-send-string` is unibyte end to end,
so only EOL conversion touches it, and every observed failure is on the **receive** side — `binary`
over-counting via `position-bytes` (guarded by `ebp-wire-test.el:1073`) and `undecided` eating the CR
(guarded now, §8).

### 4.3 Is `utf-8-unix` the right pin? — YES; two sub-claims refuted

`ebp.el:1597-1599` already pins it, with a rationale comment at `:1583-1596`. Two tempting revisions
are both wrong:

- **`utf-8-unix` does not "fail loudly"** on an unencodable character — it silently emits the raw
  byte. The loud failure lives one layer up at `json-serialize`. Do not re-argue the pin from a
  fail-loudly premise.
- **eglot's `utf-8-emacs-unix` is neither better nor worse** — 0 differences over 14,546 characters on
  encode, identical on decode. Containment 2 means the body never round-trips through the coding
  system anyway.

**One residual no pin can fix:** `position-bytes` counts internal bytes, so any invalid-UTF-8 octet
from a non-conforming peer inflates the receive-side count. Inherent to renting `jsonrpc.el`, bounded
to peers already violating §4.1.

### 4.4 A candidate fix that must NOT be implemented

The investigation proposed binding `coding-system-for-read`/`-for-write` to nil around the dial, on
the grounds that those dynamic variables *override* `:coding`. **They do not.** Live:

```
control        : (utf-8-unix . utf-8-unix)
dynamic binary : (utf-8-unix . utf-8-unix)
dynamic latin-1: (utf-8-unix . utf-8-unix)
```

and `src/process.c:3227-3240` says why — `Vcoding_system_for_read` sits in an `else if` reached only
when `:coding` is absent:

```c
tem = plist_get (contact, QCcoding);
val = Qnil;
if (!NILP (tem))                            /* explicit :coding wins outright */
  { val = tem; if (CONSP (val)) val = XCAR (val); }
else if (!NILP (Vcoding_system_for_read))   /* only when :coding is absent */
  val = Vcoding_system_for_read;
```

Recorded because it is the inverse of the usual review failure: not a real finding scored as refuted,
but a **non-existent hole proposed as a fix**, which would have shipped dead code carrying a false
comment. **Verify proposed remedies as hard as proposed findings.**

### 4.5 Candidates — **CANDIDATE, NOT RATIFIED**

Informative §24.2 note naming the `undecided` → `-dos` latch. |

| 3-c | test | Loopback regression: dispatch under the pin, **non**-dispatch under bare `undecided`. **Done** (§8). |

## §5 §13.2/§24.2 — persistent monotonic revisions across process death

### 5.1 The concern — REFUTED

**Stale absorption already works.** `ebp.el:1359-1361` absorbs on *any* non-error result, which includes
`status: "stale"`, and `ebp-client--absorb-floor` (`:1330-1334`) takes a `max`. Driven live through
the real `ebp-client--surface-request` against a §13.2-conformant stub: local floor 3 → sends 4 →
`stale` at 5 → absorbs → sends **6** → applied. No loop, no livelock. It is **already
regression-tested**: `test/ebp-wire-test.el:525` (`ebp-test-client-surface-revisions-above-floors`) drives pushes past
reported floors and absorbs both `applied` and `stale` results over the live path.

**§24.2's MUST is dischargeable.** The welcome carries *every* floor: §13.3 (`SPEC.md:1344-1346`)
requires present snapshots and tombstones, §13.1 forbids reclaiming a floor, and the Companion
implements it (`SurfaceStore.snapshot()`; `CompanionEngine.kt:2040`). §10.3 orders absorption before
any push. So an Emacs that loses its entire counter to SIGKILL re-learns every floor before it may
push. The welcome-size worry is also refuted: §4.5's reservation explicitly budgets a worst-case
`surfaces` object and `CompanionEngine.kt:2119-2158` computes and enforces it.

**The Companion side is solid:** write-to-temp → `fd.sync()` → atomic rename → directory fsync
(`SurfaceBacking.kt:126-137`), `persist()` before returning `applied` (`SurfaceStore.kt:294`),
amendment #107 implemented (`SurfaceStore.kt:91-105`).

**Android teardown is worse than assumed, and it does not matter here.** `EmacsService.onDestroy`
calls `shut_down_emacs()` directly rather than `Fkill_emacs`, and `shut_down_emacs`'s first act is
`Vrun_hooks = Qnil` — so **`kill-emacs-hook` is unreachable on that path by construction**. Write-ahead
would be the only sound persistence strategy if persistence were needed. It is not, because absorption
covers it.

**Residual, literal:** §13.1 says "Emacs MUST assign revisions monotonically per surface and MUST
persist its next revision." `ebp.el` keeps revisions in an in-memory hash (`:558`) and persists
nothing, so the letter of that MUST is unmet while its purpose is met by absorption. Recorded as a
documentation/amendment question for the drafting round, not a defect to fix blind.

### 5.2 The P1 this turned up instead — `jetpacs--applied-revisions` (app layer, NOT fixed)

There is a **second** revision store. `jetpacs--applied-revisions` (`jetpacs-surfaces.el:409`) is the
input to `jetpacs-event-stale-p` (`:416-432`), which four production handlers use to gate events
(`jetpacs-buffer.el:990`, `jetpacs-sections.el:496,687`, `jetpacs-results.el:404`). It is in-memory,
written **only** on an `applied` result (`jetpacs-shell.el:428-434`), and **never seeded from the
welcome**. When the lookup misses, `(integerp applied)` short-circuits and the function returns
**not stale**.

```
1. Emacs pushes app:main to revision 42; the Companion persists it.
2. Offline, the user taps the cached snapshot → event durably queued, revision_seen 42.
3. Emacs advances the surface to 60.  Android kills Emacs.
4. Restart: the welcome absorbs 60 into ebp-client-revisions;
   jetpacs--applied-revisions stays EMPTY.
5. queue.replay delivers the event → jetpacs-event-stale-p → nil → NOT stale
   → the handler indexes an 18-revision-old snapshot.
```

Verified live. The SYNCING push does not save it: `jetpacs-shell--before-replay` pushes only
`:required` roots, `:required` defaults to nil, and the only `:required t` in the repo is in a test.

**Prior art:** this is `docs/AUDIT-full-spec-RAW.md:1993`, logged `[P3] [unverified]`. This pass
verifies it and confirms reachability. **The P3 rating looks too low** — two snapshots at one revision
make `revision_seen` ambiguous.

**Update (2026-07-25, later the same session): C1 landed as `d11300e`** after sign-off — seed at
the §10.3 step-3 barrier via the new named `jetpacs--before-replay`, replace-not-max, tombstone
floors included; reproduced against the old wiring (`accepted`) before fixing (`stale`). Floor
suite 24 → 26. §5.3's C1 row is therefore CLOSED; C2 remains do-not-land-standalone, C3/C4 remain
open candidates.

**Not fixed in the research phase itself, deliberately.** It lives in the app-layer track (`PLAN-jetpacs-consumers.md`,
`AUDIT-jc-layer-2026-07-24.md`), needs an app-layer welcome/ready seam plus its own tests, and the

it stored), which is exactly what `jetpacs-event-stale-p`'s docstring means by "newest CONFIRMED-applied
revision, not the claimed floor", so seeding from the welcome is semantically right; but that is an
app-layer design call, not an A8 one.

**Two genuine spec holes, recorded for whenever a consumer is built:**

1. **Flattening is unspecified.** §19.5 says fontify runs "MUST NOT overlap". `xfaces.c:6884-6886`

## §7 The finding nobody had on the list — §22.3 is undischarged on the Emacs side

A8-1's own framing says it "bears on §22.3 backpressure". Following that thread past the send question
gives a finding of its own.

§22.3 (`SPEC.md:3840`): "Every endpoint MUST bound its inbound frame queue, parsed-message queue,
outstanding request count, and module-specific work queues. It MUST apply transport backpressure
before unbounded memory growth." §24.2 makes "sender-side resource limits and load management" a MUST
for a conforming Emacs endpoint. **§22.3 binds Emacs, not only the Companion.**

**The Companion discharges it** — Tier-2/LD-13: hold at 512 outstanding, resume below 128, local
`1401`; `CompanionEngine.kt:238-239`, with amendment #106 exempting the single-flight pump.

**`ebp.el` discharges none of it.** The `ebp-client` struct (`:545-586`) has no outstanding-request
counter, no inbound bound and no overload state; there is no `stop-process`, no `1401`. All three
queues §22.3 names are delegated and unbounded:

| §22.3 queue | Where it lives under jsonrpc.el | Bounded? |
|---|---|---|
| inbound frame queue | the process buffer | no |
| parsed-message queue | `jsonrpc-mqueue` (`jsonrpc.el:779`) → `timer-list` | **no** |
| outstanding request count | jsonrpc.el's continuation table | **no** |

This is the §6.2 delegation clause again. A0 bounded its *strictness* axis; §6.2 still says nothing
about a delegate's *queue bounds*, so the paragraph that licenses renting `jsonrpc.el` silently
licenses renting its unboundedness. **§23.5 already has the precedent for the fix shape** — its
interning rule ends "This obligation is not relaxed by Section 6.2: the cost is permanent and
cross-session, not per-frame." A parallel sentence for §22.3's bounds is the natural candidate.

**Backpressure is mechanically available and unused.** `stop-process`/`continue-process` on a network
process is the one lever an Emacs endpoint has. Whether it is *safe* is the open question — see §1.5:
Emacs's reading inside a blocked send is what unwedges the Companion, so a naive "stop reading when
overloaded" can convert an overload into a deadlock. **This is the sharpest constraint on any §22.3
remedy for the Emacs side, and it is why this is filed as research rather than fixed here.**

### 7.1 Sub-finding — `timer-activate` is O(n) per insert, and jsonrpc.el knows

`timer.el:161` `timer--activate`: `:178` is an **unconditional O(n) `memq`** over the whole list on
every insertion, and `:182-184` a second linear scan. jsonrpc.el's comment at `:798-801` —
"`timer-activate` orders timers by time, which is an very expensive operation when jsonrpc-mqueue is
large" — shows the authors hit this; their mitigation (reusing one `time` object, `:802`) addresses the
time comparison, not the `memq`. N pipelined frames therefore cost **O(N²)**. Practical N per filter
invocation is bounded by the read chunk, so this is a cost finding, not a hang on its own — but it
composes with the `inhibit-quit` property in §1.1.

**Ordering is nevertheless correct — a naive §7.4 concern REFUTED.** The filter pushes to the head of
`jsonrpc-mqueue` (`:775-779`, reversing wire order), the drain `pop`s (`:803`, reversing again), and
because every timer gets the same `(current-time)` (`:802`) the strict `timer--time-less-p` scan stops
at the head, so each insert lands at the front of `timer-list` — restoring wire order exactly. The
double reversal is deliberate and the library's comment at `:775-778` says so. **Do not report an
ordering defect here.**
