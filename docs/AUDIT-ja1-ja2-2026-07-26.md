## 1. Verdict

The code is **sound in posture and unsound in coverage**. Every rule it breaks is quoted correctly, in the right file, within a few lines of the violation — `jetpacs-buffer.el:591-597` names the exact budget hazard `jetpacs-chrome.el:226` then reintroduces; `jetpacs-chrome--drill` documents the mutate-then-signal trap that its three public siblings walk into; `jetpacs-clip.el:187-189` warns about the zero-arg push that `jetpacs-navigate.el:75` then performs; `jetpacs-shell.el:613-614` asserts an invariant the W10 path breaks four lines later. **The dominant theme is: the invariant was written down and then applied to exactly one of its N call sites.** The `offline.wake` grant is enforced in one emitter of three. The SPEC 4.5 budget is enforced in one builder of five and reset per screen. The deferred push is applied to one chrome verb of four. The exposure table, the ID minters, the error boundary and the render budget were all written for *one document per surface* and JA-2's chrome kit made a surface hold N.

Secondary theme, and the reason a P1 shipped through a 16/16 device gate: the test suite is strong where JC-4b counter-discipline was applied by hand and structurally blind everywhere else — no ERT file loads two new modules together, and four of this rung's seven load-time global wirings can be deleted with all 345 tests green.

What is genuinely good and should not be touched: the 25-role theme mirror (byte-exact against `contract.json` in all four modes), the node-type profile unions (B14's fix holds — zero drift in either direction across all three profiles), the SPEC 23.3 **log** discipline (`jetpacs--error-label` everywhere, zero `error-message-string` in the diff), the 18.6 closed reminder schema, the W10 `queue.replay` ceiling exemption, and the house invariants (delineation guard green, all 18 files byte-compile under `byte-compile-error-on-warn`, every `fboundp` a legitimate cross-module seam or modus-5.x library guard).

## 2. P1 findings

### P1-1 — `ebp-client--force-replay-retry` is permanently dead after the first retry cycle; the durable pump stalls for the session

**Where** `emacs/ebp.el:1136` (guard), `:1099` (the only `setf`), `:670-671` (close cancels but does not clear), consumers `emacs/jetpacs-surfaces.el:235` (`jetpacs-retry-later`) and `emacs/ebp.el:1349-1353` (receipt-commit failure).

**Rule** SPEC 15.3 — "a JSON-RPC error retains the head and pauses it… Emacs SHOULD call `queue.replay` with bounded backoff after it returns a transient error for an automatically delivered durable event" — and ratified B9 rule 3, whose entire premise is "1500 event-retry, *and here is the `queue.replay` that unpauses the pump*."

**Failure** `replay-retry-timer` is assigned in exactly one place and never set back to nil. After one full backoff cycle drains (`remaining` 0, the recursive `--schedule-replay-retry` no-ops), the slot still holds a fired timer. The guard `(unless (ebp-client-replay-retry-timer client) …)` therefore tests *has this session ever scheduled a replay*, not *is one pending*. Every later `jetpacs-retry-later` sends 1500 with no replay behind it and does not even apply its own fabricated `(:remaining 1)`. Companion-side, `pumpPaused` is set true at `CompanionEngine.kt:610` and cleared **only** in `handleQueueReplay` (`:560`) — so that event and **every later durable (`queue`/`wake`) event stalls for the rest of the session**, including reminder taps admitted while offline. Recovery requires a transport drop and a fresh §10.3 barrier. Reproduced in batch against real code (only `ebp-client--request` stubbed): after one cycle, `(memq timer timer-list)` nil, slot non-nil, and a subsequent `--force-replay-retry` sends **zero** `queue.replay`.

**Fix** Clear the slot in the timer's own lambda (`(setf (ebp-client-replay-retry-timer client) nil)` as its first form) **and** in `ebp-client-close`. That re-opens a concurrency hazard the broken guard accidentally suppressed, so pair it with an explicit `replay-in-flight` slot set before `ebp-client--request 'queue.replay` and cleared in its callback; `--force-replay-retry` consults that, and `--schedule-replay-retry` must `cancel-timer` any live predecessor before assigning.

**Why it survived the gate** see P3 `retry-tests-blind-to-dead-force`: `test/jetpacs-floor-test.el:639-640` asserts `(timerp (ebp-client-replay-retry-timer client))` *after both* retry calls — an assertion the bug is required to satisfy; `test/ebp-wire-test.el:1575` counts `>= 2` replays when the barrier already sent one; `test/smoke-ja2.el:79-85` never lets `remaining` reach 0.

### P1-2 — The chrome drill resets the SPEC 4.5 render budget per screen; one snapshot carries N × `max_rich_spans`

**Where** `emacs/jetpacs-chrome.el:226` (per-screen `jetpacs-buffer-with-budget`), `emacs/jetpacs-buffer.el:599-603` (the unconditional rebind), `emacs/jetpacs-chrome.el:111-118` (every screen walked into one `multi_view`), `emacs/jetpacs-navigate.el:49-51` (the seam contract that *mandates* the shared budget).

**Rule** SPEC.md:304-305 — "`max_canvas_ops`, `max_chart_points`, `max_rich_spans`, and `max_table_cells` are aggregate counts across one SurfaceSpec" — plus SPEC 4.5's "A sender MUST respect reported limits and MUST NOT rely on receiver truncation."

**Failure** Bites at stack depth **two**, not fifteen. The reference Companion advertises `max_rich_spans: 4096` (`DeviceBridge.kt:139`) and counts it in a single `Ctx` across every view (`SpecValidator.kt:112-113, 122-127, 705-706`). Two 400-line font-locked drill screens measured **8192 spans in one snapshot** → `1201 content-invalid` for the whole update. Per SPEC 13.2 the stored snapshot is retained, so the surface **freezes**: the drill never appears and every subsequent push of that stack is rejected identically until someone pops screens from Emacs. The byte budget resets the same way (`buffer.el:616-617` grants each screen `max_frame_bytes - 2048`), which is the path to P1-3's session kill.

**Fix** (a) make `jetpacs-buffer-with-budget` idempotent — `(let ((jetpacs-buffer-budget (or jetpacs-buffer-budget (jetpacs-buffer-budgets)))) …)` — because `jetpacs-sections.el:426` and `jetpacs-hypertext.el:991` do the same unconditional rebind and an outer wrap alone would not fix it; (b) drop the per-screen wrap at `chrome.el:226` and wrap `jetpacs-chrome--build`'s `dolist` once; (c) add a **node counter** to the budget cons — `jetpacs-sections.el:82-85` names node count as the binding constraint and nothing budgets it. Fixing (a)+(b) alone leaves 4097 spans against 4096 — see P2 `cap-spans-off-by-one`, which must land in the same commit.

> One verifier held this at P2 on the grounds that device-side back-arrow recovery exists. I am reporting P1: it is a sender MUST violation that puts a rejected document on the wire on the rung's headline feature at depth 2.

### P1-3 — There is no sender-side SPEC 4.5 **size** gate anywhere; the frame-byte path kills the connection

**Where** `emacs/jetpacs-shell.el:431-453` (`jetpacs-shell--gate-spec`), invoked at `:607`. **Verified**: it checks node types (16.2), builtins (10.2), constraining features (22.4) and 18.5 meta descriptors — and no size at all. `grep` confirms no elisp reads `max_table_cells`/`max_chart_points`/`max_canvas_ops` outside `jetpacs-hypertext.el`'s table path, and `max_frame_bytes`/`max_rich_spans` only inside `jetpacs-buffer.el`.

**Rule** SPEC.md:304-305 and SPEC 4.5's sender MUST. **No amendment is needed — the spec is already unambiguous; the sender simply doesn't check.**

**Failure** Every builder outside `jetpacs-buffer` — the chrome multi-view assembly, `jetpacs-sections`, and any third-party Tier-1 skin, which the new framing invites — can exceed a reported limit with nothing between it and the socket. Sharper than a 1201: eight stacked drill screens, each independently granted `max_frame_bytes - 2048` by P1-2's reset, produce a body over `max_frame_bytes` (4194304, SPEC.md:247); `ebp.el:334` signals `ebp-frame-close`, or the peer emits `1400 frame-too-large` and **closes the connection** per §6.2.

This is the natural home for the P1-2 and `cap-spans-off-by-one` fixes.

### (a) Chrome / multi-view composition — one document's machinery holding N documents

- **`jetpacs-chrome-push-screen` / `-pop-screen` / `-reset-screens` mutate then signal, bricking the surface.** `emacs/jetpacs-chrome.el:161-162`, `:170-172`, `:181-183`. SPEC 14.4 (`rejected` → "Delete durable record and surface a diagnostic") + B9 rule 5. A handler follows the docstring's own instruction (`chrome.el:153-155`), `--stack-insert` mutates, then `jetpacs-shell-push` signals from GATE 1/3/4 (`shell.el:322/440/463/481` are all bare `error`), which `jetpacs--dispatch` flattens to a **permanent** `rejected` for an effect that happened. Verified aggravation: the poisoned entry is rebuilt on every later push, so **every subsequent plain `jetpacs-shell-push` of that surface also signals** — unpushable for the process lifetime, with no device-side recovery if the bad screen was pushed from the root. `jetpacs-chrome--drill:220-234` documents this exact hazard and defers; the three public verbs do not. **Fix**: give them the drill's shape (`jetpacs-flow-continue` + `condition-case`, or roll the stack mutation back before re-signalling).
- **One broken screen collapses the whole multi_view to a back-less error column.** `emacs/jetpacs-chrome.el:101-118` (no per-entry `condition-case`). Reproduced: `has-views=nil`, root `column`. GATE 2 then nils `current_view` and `SurfaceStore.kt:265` clears the retained view, so the back affordance *and* the navigation state die in one push, and every rebuild reproduces it. Contradicts `shell.el:279-280`'s own stated principle ("A broken builder costs its own screen, never the whole push"). **Fix**: wrap `(funcall (cdr entry) back)` per entry and substitute an error card for that view only.
- **Duplicate node IDs across stacked screens reject the whole update.** SPEC 16.1 (SPEC.md:1976-1978); `SpecValidator.kt:110/122-126/472-473` builds one `ctx.ids` for the whole document. Most ordinary route: a hub that renders a comint buffer, then a drill into that same buffer — `jetpacs-comint.el:66` mints a purely buffer-derived id emitted as the `text_input` id at `:131`, twice. `jetpacs-sections--ids` is likewise bound per render (`sections.el:422`) with its own docstring stating the one-surface-equals-one-buffer assumption representation A breaks. The drill seam contract (`navigate.el:39-51`) lists five obligations and cross-screen uniqueness is not one. **Fix**: prefix each screen subtree's ids with the screen id at composition time, or bind a document-wide id table across `--build`; add the obligation to the seam docstring.
- **A refused push loses its `current_view` permanently.** `emacs/jetpacs-chrome.el:150-162`, `:231-236`; the three retry paths `shell.el:233`, `:246`, `:693` all push with no view. The Companion preserves the view it holds (`SurfaceStore.kt:263-270`), so the tap is silently swallowed. **The auditor's proposed fix is unsound**: `jetpacs-shell--current-view` is written only by the `view.switched` handler (`shell.el:721`) and `view.switched` is generated only by the `view.switch` builtin (`CompanionEngine.kt:286-303`) — it is stale after every Emacs-driven navigation, which is a defect in its own right (`jetpacs-shell-current-view` at `shell.el:702-708` is a public accessor that lies). **Fix**: (i) record `current-view` into the map at the point `jetpacs-shell-push` claims the revision (`shell.el:620-626`) — 13.4 makes the resulting view deterministic; (ii) remember that *this* push carried a refused `current_view` (the B8 callback at `shell.el:637-640` already knows) and re-assert that exact name on the requeue. Re-asserting on a retry is fully conforming: 13.4's SHOULD-omit applies to *background refreshes*, and a navigation retry is not one.
- **The chrome stack has no depth bound and re-renders every screen on every push.** `emacs/jetpacs-chrome.el:133-148` + `:111-118`. SPEC 22.3 ("Every endpoint MUST bound its… module-specific work queues"). Fifteen forward drills means every refresh runs `font-lock-ensure` + a 500-line render over fifteen buffers before one frame leaves. A shared budget bounds the bytes, not the O(depth) work. **Fix**: bound the stack (e.g. 8 rendered-buffer screens) and evict from the bottom.
- **`jetpacs-buffer-cap-spans` returns one span at a budget of zero.** `emacs/jetpacs-buffer.el:620-627` — `(<= max-spans 1)` fires for 0 and emits `(list (jetpacs-span "…"))`; `jetpacs-buffer-spend-spans:646-648` compounds it with `(max 1 left)`. `SpecValidator.kt:705` rejects on strict `>`, so one span over 1201s the whole surface. This is the measured residual after P1-2's fix (4097 vs 4096) and is already reachable today via `jetpacs-sections--rich` (`sections.el:237-242, 364, 384`). **Fix**: add `((<= max-spans 0) nil)` and drop the `(max 1 left)`.

### (c) W10 / refusal handling

- **A W10-refused push drains the snackbar and runs the after-push hook.** `emacs/jetpacs-shell.el:645-657`. Reproduced on HEAD for both root shapes: `snackbar=nil hooks=1 toasts=nil`. The refusal callback runs *synchronously inside* `ebp-client--request` (`ebp.el:895-903`) before `(setq revision …)` completes, so control reaches `:648` with `snack` still bound, `(setq snack nil)` at `:651` destroys the queued copy, and the `unwind-protect` restorer at `:654-657` never fires because nothing signalled. B8's requeue then re-renders with the slot empty: **the user's confirmation of a durable action is lost permanently**, which is the exact loss the requeue machinery was added to prevent. `shell.el:613-614`'s comment ("drained only after the send, so a refused push keeps the feedback") is false. **Fix**: set a refusal flag alongside the existing `jetpacs-refused-p` branch; on refusal requeue the snackbar and skip `jetpacs-shell-after-push-hook`.
- **`jetpacs-refused-p` cannot distinguish a local W10 refusal from a peer 1401.** `emacs/jetpacs-surfaces.el:191-203`; consumer `shell.el:637-640`. `respondError` (`CompanionEngine.kt:2202-2208`) puts `kind` inside `data`, so a peer refusal arrives byte-identical to ebp's synthetic plist at `ebp.el:897-900`. **1401 is a *mandatory* response code**, not a local sentinel: SPEC.md:2593 requires the Companion to answer `1401 overloaded` when `limits.max_dialogs` would be exceeded (`CompanionEngine.kt:1838-1840`, asserted by `DialogTest.kt:177-183`). Consequence at the one live consumer: an unbounded, backoff-free repush loop (reproduced: 6 attempts across 5 timer fires, pending set and timer still armed). **Fix**: tag the local refusal (`:ebp-local t` — callback-only, never serialized) and require it in the predicate; independently cap consecutive refusal-driven repushes per surface with exponential backoff.
- **`jetpacs-shell--send-remove` requeues on *any* error.** `emacs/jetpacs-shell.el:155-160`. A permanent `-32601` or `1201` is re-sent at every §10.3 barrier forever. `jetpacs-refused-p` already exists to discriminate and is used that way four hundred lines later. *(P3-severity in isolation; batch it with the W10 commit.)*

### (d) Redaction, exposure, and the wire as a sensitive sink

## 4. The Tier-1 / base boundary

Two of the five new modules are correctly-shaped mechanism, one is a whole application sitting in `emacs/`, one is mechanism welded to a product verb, and one is a kit that crosses a single policy line. Nothing in JA-1/JA-2 assumes git, magit, with-editor or transient (D-10 clean for this rung), and the pie plumbing is fully intact — `git diff c717138..HEAD -- ebp/ companion/` is **empty**, nothing was retired.

### MOVE — `jetpacs-clip.el` → the Tier-1 exemplar

It is a complete app inside base: permanent owner `"clip"`, permanent surface `app:clip`, its own action, `kill-new` advice armed by `require`, a push at registration, and a foreground-stealing default. Every piece of mechanism it needs already lives in base (`jetpacs-scalar-text`, the byte-cap helper, `jetpacs-builtin-advertised-p`, `jetpacs-clipboard-copy`, the chrome kit) — what moves is the owner, the surface, the action and the advice.

**Be precise about the authority here**: this is my recommendation, *not* a violation of a ratified decision. PLAN §7 makes any **built-in** Emacs feature base scope, and D-11 explicitly ratifies package.el's *mutating* browser as legitimate base on exactly that reasoning. The kill ring is built-in. So "clip belongs in Tier-1" is a call for Caleb; the P2 privacy defects (load-time push, no exclusion predicate, unconditional preview leak, no retraction) are **mandatory regardless of where it lives**. The boundary is simply the natural place to make the whole thing opt-in.

### SPLIT — `jetpacs-theme.el`

- **Stays base**: the palette mirror (device coherence is protocol-adjacent, and 18.4's mode choice is explicitly Emacs-side policy), and the `jetpacs-modus-*` queries at `:190-231`.
- **Moves Tier-1**: `modus.toggle` and owner `"theme"` — a theme-switching verb on a screen is an opinionated experience.
- **Required to make the split usable**: an `off` value in `jetpacs-theme-mode`, a `jetpacs-theme-payload-function`, and the modus queries in a module that carries no hooks. Without those three, a settings Tier-1 that loads the file to reach the queries has its own palette cleared on every reconnect (P2 above).

### KEEP IN BASE — `jetpacs-device.el`, `jetpacs-chrome.el`, `jetpacs-navigate.el`

- **`jetpacs-device.el`**: correct base mechanism. Claims no owner, no surface, no action, no root; `jetpacs-reminders-set` is owner-*parameterized*; its only global effect is an owner-filtered teardown hook. SPEC 18.6 is protocol and the wrapper adds no screen. **No move needed** — fix the wake gate (P1-4), the generation-counter ordering, and the `remhash` at `:174` that resets the very counter the module exists to protect.
- **`jetpacs-chrome.el`**: correct as a *kit* — no owner, no surface, no action, and it correctly subscribes to `jetpacs-shell-view-change-functions` rather than re-`defaction`ing `view.switched`. Its one policy crossing is the unconditional global seizure at `:240-241`.
- **`jetpacs-navigate.el`**: correct as a host. Same seizure caveat at `:129-130`.

### Missing seams for a third-party skin

Ordered by what blocks a Tier-1 author soonest:

1. **`jetpacs--dispatch` must bind `jetpacs-current-owner`** (`jetpacs-surfaces.el:621-628`). Without it every owner-derived default in base is a documented trap that each module hand-writes a warning about.
2. **Per-surface drill-host registry** — `jetpacs-navigate-register-drill-host SURFACE FN`, global as fallback. One global cannot serve two Tier-1s.
3. **Default-sentinel guards on seam seizure** — `(unless jetpacs-navigate-drill-function (setq …))` at `chrome.el:240-241` and `navigate.el:129-130`, matching the correct pattern at `jetpacs-surfaces.el:296-299`. Today an explicit config value survives or dies on `require` order.
4. **`jetpacs-theme-mode` `off` + `jetpacs-theme-payload-function`**, and a hook-free home for `jetpacs-modus-*`.
5. **`jetpacs-teardown-functions` must pass the surface list** — the registry is swept before the hooks run, by design (`jetpacs-surfaces.el:851-853`), so a hook cannot recompute it.
6. **`jetpacs-owned-surface-p (surface owner)`** so a D1 handler can clamp a wire-supplied surface; make it the documented idiom in `jetpacs-chrome-push-screen`'s docstring, replacing the bare `(plist-get params :surface)`.
7. **`jetpacs-event-durable-p`** off `(plist-member params :queued_at_ms)` — `CompanionEngine.kt:377-379` sets it on every `queue`/`wake` event including while READY, so it is a sound predicate — so B9 rule 4's UI carve-out is *checkable* rather than an honour system.
8. **`jetpacs--gate-descriptor-policy`** called by every non-surface descriptor emitter (P1-4).
9. **`jetpacs-pie-show` / `jetpacs-pie-dismiss`** with the parity shape of `jetpacs-toast`. D-9 retains the plumbing; the Emacs-layer verb is what a future Tier-1 will reach for, and today an invalid menu is dropped by the Companion in **total silence** (`CompanionEngine.kt:969` returns with no log; the only logged drop is the count limit).
10. **A framework-generic destructive-command predicate** to replace the 17-symbol magit denylist at `jetpacs-sections.el:99-117`, which is the only filter on a section's own keymap (`:548`, `:613`) while the mode-map path is properly allowlisted. D-10 already schedules this move to the git exemplar; kubernetes.el/forge consumers are unprotected until it happens.
11. **Per-surface snackbar** — `jetpacs-shell--snackbar` (`shell.el:56`) is one global slot drained by the next push of *any* surface, and navigate's three new `jetpacs-shell-notify` call sites have a `target` in hand and ignore it. *(P3, pre-existing since JC-0, but the new producers make it visible.)*
12. **Teardown hygiene in the app-shaped modules** — neither `jetpacs-clip` nor `jetpacs-theme` registers a `jetpacs-teardown-functions` hook, so `jetpacs-teardown-owner` leaves clip's `kill-new` advice armed and theme's `enable-theme-functions` subscription live. These two files are the templates a package author will copy; the template omits the one lifecycle hook base provides.

### Naming and ownership — already permanent, already wrong

- Owner `"clip"`, owner `"theme"`, actions `clip.refresh`, `modus.toggle`: unqualified, in a flat process-global namespace (`jetpacs--registrations`), documented by the code itself as permanent because SPEC 13.5 persists the device snapshot keyed by surface id.
- `jetpacs--claim` is **silent** on a same-owner collision even under `jetpacs-strict-namespaces` — the strict valve fires only on a *different* owner. Two packages that both pick `"clip"` silently overwrite each other's root builder and action handler; load order decides.
- **Decide now** (ratification, not code): reserve `jetpacs.*` for base and rename to `jetpacs.clip` / `jetpacs.theme` / `jetpacs-clip.refresh` / `jetpacs-theme.modus-toggle`; key `jetpacs--claim` on the defining file/feature so live-coding stays silent while cross-package takeover warns. Amendment #134 covers the wire-level policy. Every week this waits, more paired devices hold cached surfaces under the squatted names.
- **Not a risk**: drill view ids. `jetpacs-wire-id "drill" LABEL` is caller-prefixed and stacks are keyed per surface, so two Tier-1s drilling the same buffer name never collide. Leave it.

## 5. SPEC amendments needed

> **Not needed, stated plainly**: SPEC 4.5's sender obligation. SPEC.md:304-305 already reads "A sender MUST respect reported limits and MUST NOT rely on receiver truncation" and defines the aggregates per SurfaceSpec. P1-2 and P1-3 are pure implementation defects. Do not amend around them.

### #126 — SPEC 18.4: reconcile the syntax-role registry

**Hole** `meta` and `paren` are read by the reference Companion (`SyntaxHighlight.kt:95, :104`) and appear in neither SPEC.md nor `contract.json`; five registry roles (`variable`, `type`, `operator`, `preprocessor`, `tag`) are implemented nowhere. Reading an unregistered role violates SPEC.md:2708.

**Proposed text (option A — register)**
> The standard syntax roles are `comment`, `string`, `keyword`, `function`, `constant`, `variable`, `type`, `number`, `operator`, `preprocessor`, `heading`, `link`, `todo`, `done`, `tag`, `meta`, and `paren`. A Companion MUST ignore a role name outside this list and MUST NOT interpret one standard role as another. A Companion whose highlighter has no concept corresponding to a standard role MAY ignore that role; ignoring it does not license substituting a different role's style for it. A sender MAY omit any role; the Companion MUST merge a missing role with a legible platform fallback.

**Option B (delete)** — strike `meta` and `paren` from `SyntaxHighlight.kt` and drive org tags from `tag`, parens from `operator`. No spec change.

**Breaks** Option A makes `SyntaxHighlight.kt:385`'s use of `meta` for org tags non-conforming until `tag` is read, and requires `contract.json` `syntax_roles` to grow by two. Option B is a pure Kotlin change. **Either way `jetpacs-theme.el:369, 412`'s `:meta` duplicate dies.** Caleb picks.

### #127 — SPEC 18.4 + `contract.json`: make SyntaxStyle machine-checkable

**Hole** `fg` — the only member Jetpacs ever emits — is absent from `contract.json` `field_types`; there is no `syntax_style` schema; `ebp/validate.py` reads neither `theme_roles` nor `syntax_roles` (the only two top-level contract sections it ignores); and the sole `theme.set` golden (`goldens/frames.golden:21`) carries one syntax role. All three pinning rails are blind to the wire's richest payload — which is mechanically why the `meta` drift survived three rungs.

**Proposed text**
> The `SyntaxStyle` object is projected into `contract.json` as `syntax_style`, whose optional members are `fg`, `bg`, `font_weight`, `italic`, and `underline`. A conformance validator MUST check every member name of a `theme.set` `colors` object against `theme_roles`, every member name of its `syntax` object against `syntax_roles`, and every `SyntaxStyle` member against `syntax_style`. The golden corpus MUST contain at least one `theme.set` frame exercising the complete `theme_roles` set and at least three distinct syntax roles.

**Breaks** `ebp/validate.py` gains a theme check and the golden must be regenerated; both are additive.

### #128 — SPEC 13.4: the variant transition

**Hole** 13.4's three view-change conditions (SPEC.md:1399-1402) presuppose consecutive multi-view snapshots. When a chrome surface degrades to a single-root error spec and later recovers, whether the remembered view survives is unspecified. `SurfaceStore.kt:264-266` resolves it (`!isMultiView -> null`) with a rule not derivable from the text — and the builder-crash defect puts every chrome surface on that path.

**Proposed text**
> An accepted snapshot that carries no `views` clears any current view the Companion retained for that surface. The next accepted multi-view snapshot for that surface that omits `current_view` therefore selects `initial_view`.

**Breaks** Nothing — it ratifies the reference behaviour.

### #129 — SPEC 10.2: the welcome reports the current view

**Hole** `surfaces` is `{revision, present}` (SPEC.md:1061) and `view.switched` is `when_offline: drop` (SPEC.md:1577), so after a disconnect during which the user backed out locally, Emacs cannot learn the device's view at the §10.3 barrier. The navigation channel is write-only and lossy; `jetpacs-chrome.el:20-26` declares the resulting drift "BENIGN by design" — an invented policy filling this hole.

**Proposed text**
> For a present surface in the `app` namespace whose latest accepted snapshot is multi-view, the `surfaces` entry MUST also carry `current_view`, naming the view the Companion is presently showing. Emacs MAY include `current_view` in an update naming the view the Companion already shows; such an update is a no-op for navigation.

**Breaks** Additive to the welcome; the Companion already persists the value (`SurfaceBacking.kt:74, :106`).

### #130 — SPEC 8 + 22.3: `1401` as a response

**Hole** §18.1 *mandates* a `1401 overloaded` response when `max_dialogs` would be exceeded (SPEC.md:2593, `CompanionEngine.kt:1838-1840`), while §22.3 describes an identically-shaped 1401 as a purely local sender-ceiling conclusion that MUST NOT reach the wire. No clause supplies a discriminator, and none states any receiver obligation on a received 1401.

**Proposed text**
> `1401 overloaded` MAY be returned as a response `error.code` where a method's registry entry lists it. An endpoint MUST NOT conflate a `1401` received as a response with a refusal generated locally by its own sender ceiling; a locally generated refusal MUST be distinguishable from a peer response by the code path that consumes it. On receiving a `1401` response an endpoint MUST NOT resend the same request immediately: it MUST apply bounded backoff and MUST bound the number of consecutive resends. Section 24.6 gains: *a peer-returned `1401` on a request the local ceiling did not refuse, verified not to trigger unbounded local retry.*

**Breaks** Nothing normatively; it forces `jetpacs-refused-p` to carry a locality marker and the B8 requeue to gain a cap — both already required.

### #131 — SPEC 15.1 / 14.4: the durability discriminator

**Hole** B9 rule 4 blesses `accepted` + `jetpacs-flow-continue` for "UI whose loss the user can re-tap", but 14.4 states flatly that "Returning `accepted` merely because a volatile callback was scheduled is not conforming" and Emacs has **no seam** to tell a `drop` event from a durable one.

**Proposed text**
> Because Section 15.1 requires the Companion to persist a `queue` or `wake` event before every delivery attempt, including when a `READY` session already exists, the Companion MUST include `queued_at_ms` in the params of every such delivery and MUST omit it for a `drop` event. Emacs MAY treat the presence of `queued_at_ms` as proof that the Companion holds a durable record for that occurrence.

**Breaks** Promotes `queued_at_ms` from informational to constraining, so §12 rule 2 applies: a Companion may never omit it for a durable delivery. `CompanionEngine.kt:377-379` already conforms.

### #132 — SPEC 18.3: make an invalid pie menu observable

**Hole** SPEC.md:2650-2654 says "Any authored conflict makes the menu invalid" with no diagnostic duty; the only mandated `log.error` is the count limit (SPEC.md:2659-2662), and `CompanionEngine.kt:969` accordingly discards silently. A Tier-1 author's first invalid menu produces nothing anywhere on either side.

**Proposed text**
> A Companion that discards a `pie_menu.show` because the menu is invalid MUST emit `log.error` with code `1201 content-invalid`, `data.kind` `"content-invalid"`, `data.reason` `"pie-menu-invalid"`, and `data.path` naming the offending member.

**Breaks** One new log path in the reference Companion. Pairs with the base-side `jetpacs-pie-show` verb (not a spec matter).

### #133 — SPEC 18.6: `capture_fields` in a reminder `on_tap`

**Hole** SPEC 14.1 (SPEC.md:1539) makes `capture_fields` valid only inside a surface or dialog containing every named node; a reminder is neither. The elisp rejects it (`jetpacs-device.el:90-91`, citing the wrong section — 14.5 is Revision validation), the reference Companion accepts it (`validateReminder`, `CompanionEngine.kt:1138-1168`, never inspects it), and 18.5 already carries the twin rule for notification actions.

**Proposed text**
> A reminder's `on_tap` MUST NOT carry `capture_fields`. A `reminders.set` containing such a reminder is invalid; the Companion MUST reject the entire request with `1201 content-invalid` naming `on_tap.capture_fields`.

**Breaks** One new check in `validateReminder`; no conforming sender is affected.

### #134 — SPEC 4.4 / 13.1: owner-name reservation in the `app` namespace

**Hole** The spec defines surface-id syntax and the `app:` namespace but states no policy for who may claim `app:<owner>` when several independently distributed packages register inside one Emacs. Because 13.5 persists snapshots keyed by surface id, a collision is a wire-visible data hazard, not a local one.

**Proposed text**
> The `app` surface namespace is partitioned by owner. An implementation that hosts more than one independently distributed application MUST provide a reservation discipline for owner names, MUST document any prefix it reserves for itself, and MUST report a second, distinct claimant of an owner name as an error rather than silently replacing the first. Re-registration by the same claimant (as in interactive development) is not a second claimant.

**Breaks** Forces the Jetpacs rename in P1-6 and a change to `jetpacs--claim`'s identity key. That is the point: it is cheap today and expensive after third-party Tier-1s ship.

### #135 — `contract.json`: register the app multi-view variant

**Hole** `surface_spec_variants` registers only `tile`; `views`, `initial_view` and `current_view` appear nowhere in `contract.json` (0 grep hits) and `validate.py` never reads the section. The rung's central wire shape is unrepresented, so a validator generated from the contract accepts `views` on a `widget:*` or `notification:*` spec, which SPEC.md:1367-1370 requires be rejected 1201.

**Proposed text**
> `surface_spec_variants` MUST register every namespace variant defined in Section 13.4, including the `app` multi-view object with members `views` (required), `initial_view` (required), and `current_view` (optional, valid only on a request), so that a validator generated from `contract.json` rejects a multi-view object on a `widget:*`, `notification:*`, or `tile:*` surface.

**Breaks** Additive; `validate.py` gains a variant check.

### #136 — SPEC 23.3: the host library's warning sinks

**Hole** The normative sentence names "warning" among the forbidden sinks, but the informative note tells implementers that disabling the events buffer and removing the hook "satisfies this rule" — which is why `ebp.el:1852-1855` stops there while `jsonrpc--warn` keeps writing raw bodies to `*Warnings*`.

**Proposed text**
> Disabling a host library's event or trace buffer does not by itself satisfy this rule. Every warning, error, and diagnostic sink of the host library that can receive a raw frame body, a decode failure, or a message payload MUST also be disabled or redacted before the first frame is exchanged on a connection. *(Amend the informative note accordingly.)*

**Breaks** Makes the current implementation non-conforming until the `jsonrpc--warn` advice lands — which is the fix already required by P2(d).
